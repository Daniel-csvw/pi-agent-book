Agent Loop —— 两层循环，三条出路

10,800 字 · 含 585 行代码 · 约 49 分钟

上一章我们把 12 个包摊在桌上，看清了分层：coding-agent 管业务，agent 是无状态内核，ai 统一各家模型。

但架构图是静态的。Agent 之所以是 Agent，靠的是 packages/agent/src/agent-loop.ts 里那个 while (true)。

这个文件 960 行，导出 5 个函数。它是全仓库里"投入产出比"最高的一段——不到一千行，定义了所有上层共享的执行语义：CLI 的交互模式、TUI 的流式渲染、durable 的可持久化运行时、chord 的插件宿主，全都建在这套语义之上。

这一章把它拆开。读完你应该能回答三个问题：

  1. 一次 pi "找出所有 TODO" 到底发生了什么？
  2. 循环什么时候继续、什么时候停？
  3. 用户跑到一半插一句话，是怎么被"插"进去的？

一、引子：同一个模型，三种用法

假设你手里有个不错的模型，想让它"帮我改代码"。有三种做法。

模式 1：直接调用。 一次请求，一次回答。你把代码贴进去，把结果贴出来。

ts
const reply = await model.chat([{ role: "user", content: "把 foo 改成 bar" }]);

模型不知道 foo 在哪，你也没给它工具。它能做的只有猜着写。

模式 2：Workflow。 你写死流程：先读文件，再让模型改，再写回去。

ts
const before = await readFile("a.ts");const patched = await model.chat(`把这段里的 foo 改成 bar：\n${before}`);await writeFile("a.ts", patched);

这能干活了。但流程是你定的。文件太大怎么办？改错了怎么办？要不要先 grep 一下？——这些分支都得你提前想到。分支一多，你就写了个编译器，而不是在写业务。

模式 3：Agent Loop。 你给模型工具和一句目标，让它自己决定下一步。

ts
await agent.prompt("找出所有 TODO 并修复");// 它自己决定：先 grep，看到 3 处结果，再 read，再 edit，最后说"改完了"

区别不在模型，在谁掌握控制流：

控制流在谁手里 模型调用次数 能跑多久
直接调用 你的代码 1 一次
Workflow 你的代码 N（你写死） 固定步数
Agent Loop 模型 N（运行时决定） 直到模型说停

把控制流交给概率模型，代价是它可能停不下来、可能绕圈、可能在 rm -rf 之前不问一声。

所以一个能用的 Agent Loop，真正的工作量不在"循环"本身，在围住循环的那圈硬约束：步数、token、abort 信号、工具权限、输出截断、失败重试。

下面看 Pi 怎么围。

二、先把词对齐

后面会反复用到三个词，先钉死定义。

Run（一次运行）：从用户按下回车，到 agent 彻底空闲。事件流里对应 agent_start 和 agent_end。旧教程管它叫 Trace。

Turn（一轮）：一次 assistant 回应 + 它发起的全部工具调用 + 全部工具结果。一个 run 包含 N 个 turn（N ≥ 1），对应 turn_start / turn_end（packages/agent/src/types.ts:533-534）。

Event（事件）：循环向外界发出的通知。AgentEvent 一共定义了 10 种（packages/agent/src/types.ts:528-551）：

ts
export type AgentEvent =	// Agent 生命周期	| { type: "agent_start" }	| { type: "agent_end"; messages: AgentMessage[] }	// Turn 生命周期：一次 assistant 回应 + 它的工具调用与结果	| { type: "turn_start" }	| { type: "turn_end"; message: AgentMessage; toolResults: ToolResultMessage[] }	// Message 生命周期	| { type: "message_start"; message: AgentMessage }	| {			type: "message_update";			message: AgentMessage;			assistantMessageEvent: AssistantMessageEvent;	  }	| { type: "message_end"; message: AgentMessage }	// Tool 执行生命周期	| {			type: "tool_execution_start";			toolCallId: string;			toolName: string;			args: any;	  }	| {			type: "tool_execution_update";			toolCallId: string;			toolName: string;			args: any;			partialResult: any;	  }	| {			type: "tool_execution_end";			toolCallId: string;			toolName: string;			result: any;			isError: boolean;			durationMs?: number;	  };

三句话概括这三层的关系：

  • 一个 run 拆成若干 turn；
  • 一个 turn 拆成若干 message（assistant 一条，外加 N 条 toolResult）；
  • 一条 message 在流式过程中拆成若干 message_update。

循环只 emit 事件，不碰 UI。 这是它能被四种宿主复用的根本原因。

4.1 为什么 agentLoop 不是 async

看 agent-loop.ts:47-70：

ts
export function agentLoop(	prompts: AgentMessage[],	context: AgentContext,	config: AgentLoopConfig,	signal: AbortSignal | undefined,	streamFn: StreamFn,): EventStream<AgentEvent, AgentMessage[]> {	const stream = createAgentStream();	void runAgentLoop(		prompts,		context,		config,		async (event) => {			stream.push(event);		},		signal,		streamFn,	).then((messages) => {		stream.end(messages);	});	return stream;}

三个细节。

一，函数不带 async。 一旦加上，返回值就变成 Promise<EventStream>，调用方得先 await 才能拿到流——那么在第一个事件到来之前，调用方是"瞎"的，UI 没法边跑边渲染。

二，void 前缀 + .then，而不是 await。 这是"同步返回句柄、异步推进"的标准写法：void 告诉类型系统"我不关心这个 promise 的去向"，.then 只负责在结束时把结果交给流。

三，事件泵是一个箭头函数。 它满足 AgentEventSink 的定义（:35）：

ts
export type AgentEventSink = (event: AgentEvent) => Promise<void> | void;

循环不知道流的存在，只知道"有个地方能接事件"。这个缝隙让上层可以换成日志、遥测、录制回放。

4.2 agent_end 一身二职

ts

于是 agent_end 同时承担两件事：

  • 它是最后一个事件（推给 UI 的"跑完了"通知）；
  • 它同时是结果载体（stream.result() 的值）。

一个事件干两份活，省掉了"事件流 + 另一个 Promise"的配对。代价是：想知道结果，就必须等它跑完。

4.3 continue 的两道前置校验

agentLoopContinue 开头两道检查（:86-92），runAgentLoopContinue 里又重复了一遍（:144-150）：

ts
if (context.messages.length === 0) {	throw new Error("Cannot continue: no messages in context");}if (context.messages[context.messages.length - 1].role === "assistant") {	throw new Error("Cannot continue from message role: assistant");}

为什么最后一条不能是 assistant？因为 provider 要求最后一条是 user 或 toolResult——你让模型接着自己上一句话往下说，大多数 API 直接 400。

注释里（:76-78）还坦白了一件更有意思的事：

This cannot be validated here since convertToLlm is only called once per turn.

真正合不合法，取决于 convertToLlm 把 AgentMessage 转成了什么，而那一步每轮只跑一次。这里只能查"原始 role"，查不了"转换后的 role"。

能查的查到底，查不了的写进契约——这个态度在整章会反复出现。

5.2 内层在转什么

内层是"模型 ↔ 工具"的锯齿：

模型说"我要 grep" → 执行 grep → 把结果塞回去 → 模型再说 → ...

hasMoreToolCalls 就是齿距。它的赋值只有三处：

行号 赋成 含义
:189 true 进内层时先假定"还有"
:271 false 这轮没有工具调用？先按"停"算
:281 !batch.terminate 有调用，且没被全体要求终止 → 继续

注意 :271 在 if (toolCalls.length > 0) 之前。这个顺序很讲究：先默认停，再看有没有调用。没有就自然退出，逻辑上不需要 else 分支。

5.3 外层在补什么

内层停下有三种原因：没工具了、没插话了、被 terminate 了。

但"内层停了"不等于"这次 run 该结束"。外层依次问三个问题：

  1. 有 follow-up 吗？（:311）用户排着队等 agent 干完这轮再说的消息。有就塞进 pendingMessages，continue 回外层顶部，重开内层。
  2. 宿主要 continue 吗？（:320）finishTurn 上一轮返回了 {action:"continue"}，但既没工具结果也没插话。那就"用当前上下文再发一次请求"。explicitContinuation 就是给这种情况留的记号。
  3. 都没有？ break（:326）。

:305-307 那三行容易被跳过：

ts
if (hasMoreToolCalls || pendingMessages.length > 0) {	explicitContinuation = false;}

宿主要 continue，但内层本来就会再转一圈（有工具或插话）——这次请求已经被"自然满足"了，不需要外层再补。清掉记号，避免多跑一轮。

5.4 三条退出路径

退出点 条件 已 emit 的事件

:300 finishTurn 返回 {action:"end"} turn_end → agent_end

三条都以 agent_end 收尾。区别在第一类不执行工具、不调 finishTurn——模型请求本身就失败了，没有"这一轮干了什么"可汇报。

5.5 turn_start 为什么有两个发出点

翻代码会发现 turn_start 在 :127 和 :216 各发一次。会不会重复？

不会。:127 属于 runAgentLoop，只管第一个 turn；:216 在 runLoop 里，被 if (lastCompletedTurn) 包着——只有跑完过一轮才会触发。

为什么不在一个地方统一发？因为第一次进来时 lastCompletedTurn 还是 undefined，prepareNextTurn 没有可用的上下文。把第一轮交给入口函数发，runLoop 就不必区分"首次"和"后续"，少一个状态位。

runAgentLoopContinue（:155-156）做了同样的事。于是两个入口的事件序列完全一致——下游不用关心这一轮是 prompt 起的还是 continue 起的。

六、旧版的那盏信号灯，新版拆成了三盏

6.1 那张表里，三行值得单独说。

pending 是纯内部值：provider 开流时先造一条 content: [] 的 partial，done 一到就换成终态（anthropic-messages.ts:601 等 11 处），循环碰不到它。

toolUse 更有意思：类型里留着，4 个 provider 也还在发（anthropic-messages.ts:1670、openai-completions.ts:1569 等 4 处），循环已经不看它了。这是兼容性残留——UI 和 durable 的日志格式还在读这个字段，删掉会破契约。读源码时看到这种"还在产出、核心却不用"的东西，往往就是历史的断面。

deferred 最能说明分层：ai/src/types.ts:382 有这个请求选项，provider 先接单、稍后给结果，消息的 stopReason 记为 deferred 并附一个句柄。循环完全不认识它，只看到"这条消息没有 toolCall"，于是内层退出、外层问 follow-up（6.3）、没有就 agent_end——"稍后取"整个交给宿主在 finishTurn（6.4）里处理，内核一行代码都没加。不认识就按"这一轮结束了"处理，扩展点留在外面；当初若为它加个特殊分支，往后每来一个新特性都得改核心，那正是旧版把 stopReason 当信号灯的病根。ai 那边为什么只肯用一个枚举值就把这个能力换进来，M04 §3.1 讲它的另一半。

七、一次请求之前

7.1 三级流水线

streamAssistantResponse（:390-479）是唯一调用 LLM 的地方。开头三行就是三级转换：

阶段 做什么 谁实现

7.2 三个"请求前"钩子，别搞混

为什么 prepareRequest 不能注入消息？看类型定义（types.ts:180）：

7.5 第二轮的输入，到底是哪些东西

前面讲的都是"怎么转"，现在把"转的是什么"列成总账。一句话：第 2 轮发出去的，就是第 1 轮的全部输出，加上第 1 轮开始前就已经在的东西。

AgentContext 只有两个字段（types.ts:514-519）：

最后一处容易看漏：streamAssistantResponse 调 normalizeContext 时只传了 messages（:406），看起来像空转。它确实是空转——折叠 systemPrompt 和 tools 那部分（ai/src/utils/transcript.ts:30-34）在这条链上没活干，因为 Agent 层早把两样都写成 system 消息了。那为什么还要调？因为 TranscriptContext 是个带 brand 的类型，只有 normalizeContext() 能造出来：

  • addedPartial（:422）：有的 provider 不发 start，直接给 done。这时数组里没有占位，得 push 而不是替换（:458-460），还得补发一次 message_start（:462）。
  • 循环体外还有一份收尾（:470-478）：流正常结束却没发 done / error 的情况。同一段逻辑写两遍，是"不信 provider"的又一个例子。

还有一行很隐蔽（:419）：

终态消息上额外盖了一个 thinkingLevel 字段。"这条消息是在什么思考等级下产生的"只有循环知道——provider 的响应里没有。在边界上打标，别指望下游能推出来。

8.1 provider 吐 12 种事件，这里只写了 4 个分支

switch 里看着只有 start / 一堆 case 并列 / done / error，但 default 那支挡住了 9 种事件。为什么能合并？

provider 的流事件大致长这样：

text
starttext_start      text_delta      text_endthinking_start  thinking_delta  thinking_endtoolcall_start  toolcall_delta  toolcall_enddoneerror

12 种。其中 9 种是"某个块正在长"，处理方式完全一样：把 partialMessage 换成新快照，发一个 message_update。

关键在 event.partial 是累积快照，不是增量。如果它只带这一小段文本，这里就得自己维护"第几个 content block、拼到第几个字符、thinking 和 text 怎么交错"。provider 直接给全量快照，循环里就只剩一句赋值。

代价是每次 emit 都要 { ...partialMessage } 浅拷一份。为什么不直接传 partialMessage？因为下游可能把它存起来（TUI 要缓存上一次渲染结果做 diff），传引用的话，下一次事件一到，缓存里那份"快照"就悄悄地变了。浅拷贝是给订阅者的隔离带。

再看 for await 结束后那段（:470-478）：流正常结束却没发 done/error，代码还会再走一遍定稿。同一段逻辑写两遍，是"不信 provider"的又一个例子——这里的 provider 可能是浏览器里的 fetch polyfill，也可能是某个实现漏了收尾事件。

还有一个极易忽略的细节：case "done" 里面是 return finalMessage 而不是 break。因为这个 switch 在 for await 里面，break 只会跳出 switch，然后继续等下一个事件。如果 provider 之后不再发、直接关流，for await 正常结束，于是落到循环体后面那段收尾——message_end 会被 emit 两次。return 是为了就地截断。

failToolCallsFromTruncatedMessage 返回 terminate: false（:512），所以模型会收到 N 条"你的调用被截断了，请重发"，循环继续——给它自己修复的机会。

9.6 并行版的类型把戏：一个数组装两种东西

executeToolCallsParallel 里有个不太常见的类型（:698）：

ts

数组里既能放"已经定稿的结果"，也能放"一个还没跑的 thunk"。为什么要混？

因为预检（prepareToolCall）是串行的，而且可能立刻失败：工具不存在、参数校验不过、beforeToolCall 拦下——这些不需要执行，结果当场就有。如果也包成 thunk，Promise.all 里就要多绕一层没必要的异步。

于是 :615-627 遇到 immediate 直接定稿、立刻 emit tool_execution_end、塞进数组；只有真正要执行的才包成闭包（:629）。

最后 Promise.all 那一句（:656-658）：

ts
const orderedFinalizedCalls = await Promise.all(	finalizedCalls.map((entry) =>		typeof entry === "function" ? entry() : Promise.resolve(entry),	),);

typeof entry === "function" 是唯一的判别式。用函数做"惰性值"的标记，省掉了一层包装类型；代价是只要有人往数组里塞一个函数值，就会被误当成 thunk。这里安全，因为数组只有两个生产者，且工具结果里不会有裸函数。

真正值钱的是 Promise.all 的保序性：它按输入顺序返回，不按完成顺序。所以 orderedFinalizedCalls 天生就是源序，后面 for 循环 emit message_start / message_end 时不用排序。

这和事件流形成了一个有趣的错位：tool_execution_end 在 thunk 里发（:648），按完成顺序到达 UI；toolResult 消息在 Promise.all 之后发（:660-664），按源顺序进 transcript。同一个批次，两条时间线。

工具可以边跑边吐增量（读大文件时先给前 100 行）。这些 emit 是异步的，如果在回调里直接 await，会把工具自己的执行卡住。所以先 push 进数组，执行完再 Promise.all 一次性等。

二，acceptingUpdates 在 finally 里也要关。

ts
} catch (error) {	// ...	acceptingUpdates = false;	await Promise.all(updateEvents);	// ...} finally {	acceptingUpdates = false;}

finally 里那句看着冗余——成功和失败分支都关了。但它防的是第三种情况：工具在返回之后还异步调了一次 onUpdate。那时结果已经定稿，再 emit 就会拿旧数据覆盖终态。finally 保证"出了这个函数，这扇门一定关着"。

三，durationMs 用 performance.now()，不是 Date.now()。

ts
const startedAt = performance.now();const elapsed = () => Math.round(performance.now() - startedAt);

Date.now() 受系统时钟调校影响（NTP 同步、用户改时间），测出来可能是负的。performance.now() 是单调时钟。

这个数字最后会进 tool_execution_end 事件（:936）和 toolResult 消息（:951）。它不参与模型决策，但 TUI 要靠它显示"这个工具跑了 1.2s"。

十、失败也是消息

如果只能记住一条设计原则，就记这条：内核不 reject，失败也是一条消息。

三个层次。

层一：工具失败。 工具不存在、参数不合法、钩子抛异常、工具自己 throw，全部转成 createErrorToolResult（:922-927）：

ts
function createErrorToolResult(message: string): AgentToolResult<any> {	return { content: [{ type: "text", text: message }], details: {} };}

模型看到的是"你的调用错了，原因是 X"，它可以换个参数重试。这条路径不中断循环。

runToolCall 的文档注释（:818-819）把契约写死了：

Never rejects for tool failures: unknown tools, validation errors, blocked calls, and thrown errors come back as isError: true.

层二：模型失败。 stopReason 为 error 或 aborted 时，:254-265 收尾退出，但仍然 emit 完整的 turn_end + agent_end。

为什么 abort 也走这条路？因为 UI 需要一个"结束了"的信号把 spinner 关掉。abort 不是异常，是一种正常结局。

层三：外壳异常。 Agent.runWithLifecycle 的 catch（agent.ts:535-537）调 handleRunFailure（:542-558），合成一条假的 assistant 消息：

ts
const failureMessage = {	role: "assistant",	content: [{ type: "text", text: "" }],	api: this._state.model.api,	provider: this._state.model.provider,	model: this._state.model.id,	usage: EMPTY_USAGE,	stopReason: aborted ? "aborted" : "error",	errorMessage: error instanceof Error ? error.message : String(error),	timestamp: Date.now(),} satisfies AgentMessage;

末尾那个 satisfies 是本章第一次用到：意思是"按 AgentMessage 的形状检查这个 字面量，但别把我的类型放宽成 AgentMessage"。它和 : AgentMessage 差在哪， 附录 B §2.6 有三行对照。

然后照常发 message_start / message_end / turn_end / agent_end。

这样外部消费者只有一条路径要处理：订阅事件，等 agent_end。不需要 try/catch，不需要区分"正常结束"和"崩了"。

代价是：真实异常被降级成了数据，调试时得看 errorMessage 字段。这是个权衡——把复杂度从"N 个调用方"收敛到"内核的一处"。

三层的可恢复性完全不同，这是设计时就得想清楚的：

层 谁看到 能否自愈 循环继续吗
工具失败 模型（toolResult） 能，换参数重试 继续
模型失败 UI / 宿主 不能，run 结束 结束
外壳异常 所有人 不能，run 结束 结束

只有第一层是"把错误交还给模型"，后两层都是"把错误交还给调用方"。

界线画在哪里？不在"错在哪一层"，而在谁能修。参数写错了模型能改；provider 挂了它改不了。

这条界线也解释了为什么 stopReason === "length" 被归到第一层而不是第二层（9.5 节）：截断虽然发生在 provider 那边，但修复动作（重发一个参数更完整的调用）在模型这一侧。

判断错误归属前，先问"谁能修"。这个问题比"谁弄错的"有用得多——前者决定代码怎么写，后者只能决定日志怎么写。

十一、Agent：有状态的那层

agent-loop.ts 是无状态的：给它 context，它跑，返回新消息。agent.ts 的 Agent 类负责"记住跑过什么"。

11.1 systemPrompt 是算出来的

createMutableAgentState（agent.ts:83-112）：

ts
let messages = initialState?.messages?.slice() ?? systemPrompt 不是一个字段，是一个 getter。每次读，都从 messages 里把 system 消息"重放"出来。

AgentState 的注释（types.ts:384-388）也写明它是只读的：

Read-only: to change the prompt, append a system message with content or sections.

回到 §7.3 那条哲学：单一事实源。想改提示词？追加消息，别改字段。字段和列表一旦并存，就一定会不一致。

这也解释了 reset()（agent.ts:364-377）为什么是"只留下 baseline system 消息"：

ts

清空对话，但保留"你是谁"。

11.2 单飞

runWithLifecycle（agent.ts:517-540）开头：

ts
if (this.activeRun) {	throw new Error("Agent is already processing.");}

一个 Agent 实例同时只能跑一个 run。想插话？steer()；想排队？followUp()（agent.ts:383-387 的错误信息直接把这两条路指出来了）。

这个约束换来了什么？this.state 无锁可读，abort() 只需一个 AbortController，waitForIdle() 只需 await 一个 promise。

如果改成允许并发 run，state 就得加锁，事件顺序也得定义"交错规则"。不值得。

11.3 reducer

processEvents（agent.ts:575-622）把事件流折叠成状态：

事件 状态变化
message_start streamingMessage = message
message_update streamingMessage = message
message_end streamingMessage = undefined，messages.push(message)
tool_execution_start pendingToolCalls.add(id)
tool_execution_end pendingToolCalls.delete(id)
turn_end 若 assistant 带 errorMessage → 记到 state.errorMessage
agent_end streamingMessage = undefined

注意这里 messages.push 的是事件里的消息，不是循环内部的数组。Agent 自己维护一份 transcript，靠事件同步。

所以 Agent.state.messages 和 runLoop 里的 currentContext.messages 是两份数据。内容一致（因为事件就是那边 push 时发的），但对象不同。

11.4 agent_end 不等于 idle

这是最容易踩的理解偏差。types.ts:524-527 的注释：

agent_end is the last event emitted for a run, but awaited Agent.subscribe() listeners for that event are still part of run settlement. The agent becomes idle only after those listeners finish.

也就是说：

text
emit agent_end ─────► 监听器 await 完 ─────► finishRun() ─────► idle       ↑                                                            ↑  事件层跑完了                                        waitForIdle() 才 resolve

为什么这么设计？因为监听器可能要写磁盘、发网络请求、更新数据库。如果 agent_end 一发就算空闲，用户马上发下一条，两个 run 就会竞争同一份持久化资源。

processEvents 会把每个 listener 依次 await（agent.ts:619-621）：

ts
for (const listener of this.listeners) {	await listener(event, signal);}

串行 await，按订阅顺序。慢监听器会拖慢 run 的收尾——这是"顺序可预测"换来的代价。

十三、工程暗坑

1. runAgentLoopContinue 会污染你传进去的数组。

runAgentLoop 建了新数组（:121-124）：

ts
const currentContext: AgentContext = {	...context,	messages: [...context.messages, ...initialMessages],   // 新数组};

但 runAgentLoopContinue 只做了浅拷贝（:153）：

ts
const currentContext: AgentContext = { ...context };   // messages 引用未变

后续 context.messages.push(...)（:223、:284、:428）会直接写进你传进来的那个数组。

Agent 不会踩到，因为它传的是快照（agent.ts:469-474）：

ts
private createContextSnapshot(): AgentContext {	return {		messages: this._state.messages.slice(),		tools: this._state.tools.slice(),	};}

直接调低级 API 的人会踩到。绕过办法：调用前自己 .slice()。

2. partialMessage 是原地替换，浅拷贝会看到"对象没变但内容变了"。

:444 是 context.messages[i] = partialMessage——数组元素被换成新对象。但 emit 时传的是 { ...partialMessage }（:448），所以 UI 拿到的是快照。

如果你在监听器里存了 event.message 的引用并指望它"持续更新"——不会，每次都是新对象。反过来，如果你存了 context.messages 的引用，会看到它"悄悄变了"。

3. agentLoop 的 streamFn 类型必填，运行时却有兜底。

签名要求传（:52），内部却是 streamFn ?? getDefaultStreamFn()（:133）。传 undefined 也能跑，前提是 setDefaultStreamFn 被调过（stream-fn.ts:11-13），否则抛 No default stream function configured（stream-fn.ts:17）。

这个兜底存在的理由是：Agent 允许不传 streamFn（agent.ts:244），而它内部要调 runAgentLoop。M02 §8.1 的另一半——"调用由注入决定"——在这里就是这行 ??：类型要求必填，运行期允许宿主从外面塞。

4. one-at-a-time 意味着插话会排队，可能等好几轮。

默认 steeringMode 是 "one-at-a-time"（agent.ts:255）。连插三句，第一句在下一个 drain 点生效，第二、三句要再等。想一次性全塞，设 steeringMode = "all"。

5. 串行降级是整批的，不是单个的。

只要这批里有一个工具是 executionMode: "sequential"，其他本来能并行的也一起变串行（:529）。如果 edit 是串行的，而模型一次发了 1 个 edit + 5 个 read，6 个全串行。想快就把只读工具安排到别的批次，或者接受这个保守选择。

6. terminate 用 every，别误以为"任意一个就能停"。

result.terminate = true 只在本批全部结果为 true 时生效（:700-702）。单条工具想中断，得在 beforeToolCall 里 block + terminate，并且确保其他工具也这么做——否则不生效。

7. 中止时可能留下"半批"工具结果。

executeToolCallsSequential 的 signal?.aborted 检查在 push 之后（:585-587）：一旦发现中止，剩下的工具不再执行。于是 assistant 消息里发了 3 个 toolCall，transcript 里只有 1 个 toolResult。

这破坏了"每个 toolCall 必须有对应 toolResult"的不变量。循环自己不检查 signal——它把 signal 一路传进 streamAssistantResponse，靠 provider 在发请求时抛 AbortError 把下一轮变成 stopReason: "aborted"，从 :254 退出。

如果你自己实现 streamFn 并忽略 signal，就会带着一个残缺的批次去请求，多数 API 直接 400。

并行版同理，只是位置不同（:651）：先 push 进数组再检查中止，所以已经进数组的 thunk 仍会被 Promise.all 执行，在内部再检查一次然后返回 Operation aborted（:630-638）。预检通过的工具不会因为中止被跳过，只会被"执行成失败"。

8. agent_end 里的 messages 是同一个数组引用。

:263、:299、:329 三处都是 emit({ type: "agent_end", messages: newMessages })，而 runAgentLoop 最后 return newMessages——同一个对象。

订阅者在 agent_end 里 messages.push(...) 会直接改掉 run 的返回值，也会改到 stream.result() 的结果。要改就 [...messages]。

（这条和 §5.6 的 turn.newMessages 是同一个坑，只是发生得更晚。）

9. finishTurn 抛异常会从 runLoop 直接冒出去。

:261 和 :295 都是裸 await config.finishTurn?.(...)，没有 try/catch。钩子里一个未捕获的 rejection，会让整个 runLoop reject——然后被 Agent.runWithLifecycle 的 catch 接住（agent.ts:535-536），调 handleRunFailure 合成一条假消息。

后果比想象的重：:295 抛出时，下一行的 turn_end（:296）根本不会发，agent_end 里也不包含这一轮已经跑完的工具结果。工具白跑了。

对比 afterToolCall：它被 try/catch 包着（:881-911），炸了最多丢一个结果。同样是宿主钩子，两道保险差这么多，写的时候得心里有数。

10. declareToolChanges 有时返回新数组、有时返回原数组。

:364 和 :367 两处 return pendingMessages 是原引用，:365 和 :371 是新数组。所以拿返回值做 === 判断"有没有变"，会在没变时得到 true、变了得到 false。

它还会被调两次：:119 注入 prompt 时、:220 注入 pending 时。第二次的入参是 [...preparedMessages, ...pendingMessages]，一个新数组。所以"传进去再传回来"不保证同一性，别在它上面挂状态。

十四、三个可以带走的方法

方法一：双层循环——内层管锯齿，外层管续命。

内层 while (hasMoreToolCalls || pendingMessages.length > 0) 处理"模型↔工具"的往复；外层 while (true) 处理"这轮完了还要不要继续"。

把两个关注点混进一个循环，退出条件会变成一团与或非。分开之后，内层的退出只看"还能不能转"，外层的退出只看"还有没有理由继续"。

方法二：并行执行，顺序记账。

预检串行（可能问用户、查权限）、执行并发（Promise.all）、结果按原序组装（orderedFinalizedCalls）。

这保证了 transcript 的可重放性：同样的输入，重放出来的消息序列完全一致。缓存、断点恢复、审计日志全依赖这一点。

方法三：失败也是消息。

工具不存在、参数非法、被拦截、抛异常、模型报错、外壳崩溃——全部降级成一条带 isError 的消息，或一条 stopReason: "error" 的 assistant 消息。

调用方只需处理一条路径：订阅事件，等 agent_end。内核把"N 种失败"收敛成"1 种数据"。
