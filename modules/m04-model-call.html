一行。它背后是 packages/ai 的 28,551 行、204 个文件。

一、四个维度同时不一致

先说清楚要解决什么。

假设用户说了句"帮我读一下 main.ts"。在 Pi 内部它是一条统一消息：

ts
{ role: "user", content: "帮我读一下 main.ts", timestamp: 1748697600000 }

发给不同 provider，得翻译成四种样子：

text
Anthropic    { role: "user", content: [{ type: "text", text: "..." }] }OpenAI       { role: "user", content: "..." }Google       { role: "user", parts: [{ text: "..." }] }Bedrock      { role: "user", content: [{ text: "..." }] }

四种。差异点各不同：Anthropic 要数组加 type，Google 把 content 改名 parts，Bedrock 学 Anthropic 但不要 type。

纯文本是最简单的情况。真正的差异有四个维度：

维度 差在哪 一个例子
消息格式 字段名、结构、工具结果挂在哪 Anthropic 把工具结果塞进 user 消息，OpenAI 用独立 role: "tool"
流式传输 谁来解析字节流 Anthropic 返原始 SSE 要自己拆，OpenAI 的 SDK 直接给结构化 chunk
思考参数 怎么表达"多想想" Anthropic 给 token 预算，OpenAI 给努力程度，Google 给 thinkingConfig
缓存标记 怎么标记"这段没变" Anthropic 贴 cache_control，Bedrock 插独立 cachePoint 节点

四个维度乘以十个 API，就是这一层的全部工作量。

二、分三层，但真正解耦的只有一条线

Pi 的切法：

text
第一层  入口        stream() / streamSimple()      查表 + 派活第二层  事件协议     AssistantMessageEvent（12 种）  约定输出第三层  翻译器        api/*.ts                     一种方言一个文件

类比国际翻译公司：前台查通讯录派活，翻译员各懂一门语言，但交付的报告必须用公司统一模板。前台不懂外语，翻译员不懂流程。

这个类比的要害是：第一层和第三层之间只靠第二层连接，互不知道对方存在。

但这里有一个比"三层"更重要的设计，藏在入口函数的第一行。

2.1 入口里藏了一个折叠动作

stream() 的骨架（compat.ts:252-267）：

ts
export function stream<TApi extends Api>(	model: Model<TApi>,	context: Context,	options?: ProviderStreamOptions,): AssistantMessageEventStream {	const transcript = normalizeContext(context);            // ← 这一行	const builtinProvider = getBuiltinProviderForModel(model);	if (builtinProvider) {		// ... cloudflare 岔路，见 2.3		return builtinProvider.stream(model, transcript, ...);	}	const provider = resolveApiProvider(model.api);	return provider.stream(model, transcript, ...);}

normalizeContext 在 utils/transcript.ts:30-34，全文只有五行：

ts
export function normalizeContext(context: Context): TranscriptContext {	const initialMessage = createInitialSystemMessage(		context.systemPrompt,		context.tools,	);	const messages = initialMessage		? [initialMessage, ...context.messages]		: context.messages;	return { messages } as TranscriptContext;}

它把 Context（三个字段：systemPrompt、tools、messages）压成 TranscriptContext（一个字段：messages）。

系统提示词和工具定义被折进了首条消息。 再看 createInitialSystemMessage（transcript.ts:10-23）：

ts
export function createInitialSystemMessage(	systemPrompt: string | undefined,	tools: Tool[] | undefined,): SystemMessage | undefined {	const hasSystemPrompt = systemPrompt !== undefined && systemPrompt.length > 0;	const hasTools = tools !== undefined && tools.length > 0;	if (!hasSystemPrompt && !hasTools) return undefined;	return {		role: "system",		content: systemPrompt ?? "",		...(hasTools ? { toolsAdded: tools } : {}),		timestamp: 0,	};}

注意 toolsAdded 这个名字。M03 第七节讲"变更即追加"时说过：工具集变化靠 system 消息的 toolsAdded / toolsRemoved 表达。这里就是那个字段的第一次写入。

两件事在这里合上了：

text
Context.tools  ──折进──→  messages[0].toolsAdded                                │                                ↓                        getCurrentTools(messages)  累加得出当前工具集

所以"工具集从 transcript 算出来"不是个精巧的算法，是因为源头就只有这一份数据。系统提示词同理——它不在别处，就在首条 system 消息的 content 里。

一个 Context 只有一种表示形式，就是 messages。 这是整个 ai 层最省事的一个决定：provider 只需要处理"一个消息数组"，不需要知道 system prompt 和 tools 是独立概念。

顺带一个反直觉的地方：timestamp: 0。为什么不是 Date.now()？因为这条消息是推导出来的，不是"发生过的事件"。给它一个假时间戳才能保证同一次请求两次归一化产生字节完全相同的结果——2.2 和第七节的缓存都依赖这一点。

2.2 这条折叠有代价

代价是：首条 system 消息不能随便删。

压缩（M09）要扔掉老消息时，必须保住首条 system 消息，否则系统提示词和工具定义一起没了。你在 coding-agent 里看到的"压缩时总是保留开头"不是保守，是结构上的必须。

第二个代价是语义变窄：Context 上那个 systemPrompt 一旦折进去，就再也拿不回来了。想在请求途中"改一句系统提示词"，唯一合法的做法是追加一条新的 system 消息（带 sections），而不是改第一条。M03 的"变更即追加"在 ai 层不是风格选择，是这个折叠逼出来的唯一解。

2.3 派活有两条路，还有一条岔路

stream() 里的 if (builtinProvider) 藏着三档优先级：

text
① builtin provider   compatModels.getProvider(provider) 里登记过的② registry           registerApiProvider() 现注册的（扩展、测试、faux）③ cloudflare 岔路     provider 名以 "cloudflare-" 开头且没有 key

判断函数 getBuiltinProviderForModel（compat.ts:238-242）：

ts
function getBuiltinProviderForModel(model: Model<Api>) {	if (getApiProvider(model.api) !==		builtinApiProviderInstances.get(model.api)) return undefined;	const provider = compatModels.getProvider(model.provider);	const sameApi = provider?.getModels()		.some((candidate) => candidate.api === model.api);	return sameApi ? provider : undefined;}

第一行是身份比较，不是值比较。getApiProvider(model.api) 拿的是注册表里的当前实例，builtinApiProviderInstances 存的是内置实现。两者不等，说明有人用 registerApiProvider 覆盖了这个 api——此时必须让位，否则扩展就永远盖不掉内置实现。

这个设计在测试里很关键：providers/faux.ts（733 行）就是靠注册一个假 api 来让整个 Agent 循环在无网络环境下跑通。如果内置实现优先级硬编码在前，整套测试就没法做。

没有 builtin provider 时走 resolveApiProvider（:244-250）：

ts
function resolveApiProvider(api: Api) {	const provider = getApiProvider(api);	if (!provider) {		throw new Error(`No API provider registered for api: ${api}`);	}	return provider;}

这是一个同步抛出——记下来，第四节要用。

第三条岔路是 Cloudflare：

ts
if (model.provider.startsWith("cloudflare-") &&	!hasResolvedCloudflareAuth(options)) {	return compatModels.stream(model, transcript, options);}

Cloudflare Workers AI 可以走 binding（进程内对象调用，根本没有 API key 的概念），这时不能走普通翻译器那条路。这类"平台特例"在任何多 provider 系统里都会长出来，Pi 的处理是只加一个 if，不污染抽象。

2.4 这个入口本身是临时的

看 compat.ts 的文件头注释（:1-11）：

Temporary compatibility entrypoint preserving the old global pi-ai API surface... This module is deleted with the coding-agent ModelManager migration. New code uses createModels() and the provider factories.

也就是说，我们刚拆的 stream() 是一个兼容门面，v1.4.0 之后会被删掉。

那这一章还值得读吗？值得，因为新入口做的是同一件事。看 ModelsImpl.stream（models.ts:901-919）：

ts
stream<TApi extends Api>(...): AssistantMessageEventStream {	const transcript = normalizeContext(context);          // ← 同一行	return lazyStream(model, async () => {		const provider = this.requireChatProvider(model);		const { requestModel, requestOptions } =			await this.applyAuth(model, options);		return provider.stream(requestModel, transcript, requestOptions);	}, observeModelRequest(model, options, false));}

normalizeContext 还在第一行。同一个折叠，写了两遍——这恰恰证明它是结构不变量，不是兼容层的偶然。

区别在两处，都很值得看：

  • 旧门面先解析 provider，再返回流；新入口把解析塞进 async () => {}，先返回流。这个差异直接影响错误策略（见 5.3）。
  • 新入口多了一步 applyAuth：鉴权从"读环境变量"升级成了可插拔的凭据存储。

index.ts 开头的四行注释把整套分层写死了：

Core only, side-effect free: no generated catalogs, no provider factories, no api-registry, no OAuth implementations, no compat.

@earendil-works/pi-ai 是纯内核，provider 工厂在 /providers/*，api 实现在 /api/*，旧全局 API 在 /compat。一个包四个入口，靠子路径切开依赖性，而不是靠 tree-shaking 事后补救。

三、第二层：12 种事件

AssistantMessageEvent（types.ts:823-839）一共 12 个成员。下面这张表可以当查表用：

# type 额外字段 含义
1 start — 流建立，内容还没到
2 text_start contentIndex 一个文字块开始
3 text_delta contentIndex delta 推了一小段文字
4 text_end contentIndex content 文字块定稿
5 thinking_start contentIndex 思考块开始
6 thinking_delta contentIndex delta 推了一段思考
7 thinking_end contentIndex content 思考块定稿
8 toolcall_start contentIndex 工具调用开始
9 toolcall_delta contentIndex delta 推了一段 JSON
10 toolcall_end contentIndex toolCall 参数已可解析
11 done reason message 正常结束
12 error reason error 失败结束

除了 contentIndex 和 delta 这类差异字段，10 个事件还都带 partial（1 到 10 号），只有 done / error 不带——因为这两个不是"过程中的一帧"，是终局。

不用记 12 个。记模式：三类内容 × 三步 + 两头。

text
start  text_start      → text_delta      → text_end  thinking_start  → thinking_delta  → thinking_end  toolcall_start  → toolcall_delta  → toolcall_enddone | error

为什么每类都是三步？因为流式。先声明"文字要开始了"，然后逐字推，最后说"文字结束了"。

contentIndex 是这块内容在 content[] 数组里的下标。一轮回复可以同时有思考、文字、多个工具调用，靠这个下标区分。

3.1 done 的 reason 是四选一，不是三选一

ts
| { type: "done"; reason: ...; message: AssistantMessage }| { type: "error"; reason: ...; error: AssistantMessage };

那两个 ... 展开分别是：

ts
done   → Extract<StopReason, "stop" | "length" | "toolUse" | "deferred">error  → Extract<StopReason, "aborted" | "error">

大部分资料只写 stop / length / toolUse 三个。v1.4.0 有第四个：deferred——provider 说"这活儿长，我给你个句柄，你过一会儿再来取"。

这是 options.deferred 打开的能力（types.ts:381-382）：

ts
/** Ask a capable provider to return a durable handle and *  continue the request asynchronously. */deferred?: boolean | { window?: "15m" | "1h" | "24h" };

deferred 不在 12 种事件里另开一个类型，它只是 done 的一个 reason 值。这个选择很省：Agent 循环不需要认识"延迟"这个概念，它只会看到"这轮结束，但没调用工具"，于是正常收尾。M03 第六节说的"deferred 内核完全不认识，自然收尾"就是这个意思。

一个能力可以只用一个枚举值换进来。 这是加扩展时最便宜的位置——不动协议，不动消费方。

3.2 partial 不是快照

types.ts 在事件定义上方写了 16 行注释，其中最要命的一句：

partial is the shared live response-so-far helper, not an event-time snapshot.

它是"到目前为止的活响应"，不是某一刻的快照。 也就是说，如果你把 event.partial 存进数组，之后所有元素都会变成最后一次的状态——因为它们是同一个对象。

M03 第八节讲过循环那边怎么处理（每次 { ...partialMessage } 浅拷一份）。这里补充另一半：为什么 provider 不直接给增量？

因为增量要求消费者维护状态机："这是第几个 block、拼到第几个字符、thinking 和 text 交错怎么办"。全量快照把这些全免了——消费者只需要"覆盖"。

代价是每次事件都传一份完整消息，带宽略大。这是典型的用带宽换状态。

3.3 contentIndex 和"活引用"合起来会咬人

单看两条都没问题，合起来有个坑：你不可能只记下 partial 的一个片段。

ts
const textSoFar = new Map<number, string>();session.subscribe((e) => {	if (e.type === "text_delta") {		// 想"只存当前这块文字"——做不到，因为 partial 是整条消息		textSoFar.set(e.contentIndex, e.partial.content[e.contentIndex].text);	}});

这行看着对，其实读的是整条消息的第 N 个 block，不是"第 N 个 delta"。如果 partial 恰好在这一帧把后面的 block 也填了（某些 provider 会提前把工具调用参数塞进来），你读到的就不是你以为的那块。

正确姿势只有两个：要么整体浅拷贝（{ ...e.partial }），要么只用 e.delta 自己拼。不要混用——delta 是增量，partial 是全量，混着读会出现"文字重复一遍"这种经典 bug。

3.4 流对象自己也有终局

前 12 种事件都是"给 for await 看的"。但流对象还有另一个出口，不走迭代器：result()。

实现在 utils/event-stream.ts，一共 135 行。核心是 EventStream<T, R> 里的两个队列和一段 push：

ts
push(event: T): void {	if (this.done) return;                        // ① 终局之后直接丢	if (this.isComplete(event)) {		this.done = true;		this.resolveFinalResult(this.extractResult(event));	}	const waiter = this.waiting.dequeue();        // ② 有人在等就直接给	if (waiter) waiter({ value: event, done: false });	else this.queue.enqueue(event);               // ③ 没人等就排队}

三个决定：终局之后 push 一律丢弃（provider 多发一个 done 不会炸）；有消费者挂起时零延迟直送；没有就入队，等下次迭代来取。

迭代器那边正好是三种情况：

ts
while (true) {	if (this.queue.length > 0) yield this.queue.dequeue()!;	else if (this.done) return;	else yield await new Promise((r) => this.waiting.enqueue(r));}

AssistantMessageEventStream（:97-130）只是在这个骨架上加了计时：创建时记下 Date.now() 和 performance.now()，在 done / error / end 时给消息补一个 durationMs。跳过条件写得很细，其中一条值得注意——message.timestamp < this.#startedAt 时不计时，因为这条消息是别处产生的（比如 deferred 之后取回来的），不该算这个流的耗时。这一行是给延迟结果准备的。

最要紧的一点在构造函数里（:101-113）：

ts
super(	(event) => event.type === "done" || event.type === "error",	(event) => event.type === "done" ? event.message : event.error,);

extractResult 对 error 事件返回的是 event.error，不是抛异常。而 complete() 就是 stream(...).result()（compat.ts:269-276）。于是：

ts
const msg = await complete(model, context);   // 失败也不抛if (msg.stopReason === "error") { /* 只有这里能知道 */ }

await complete() 在鉴权失败、网络断开时不会 reject，它返回一条 stopReason: "error" 的消息。 这是"失败也是消息"的最后一块拼图——不只是协议层这么约定，连"等最终结果"这个 API 都照着它实现。

想用异常流只有两条路：自己检查 stopReason，或者拿 streamSimple() 手动迭代。

四、第三层：四条契约

StreamFunction 的定义（types.ts:398-402）就三行，但上面有 8 行注释，是这套抽象真正的宪法：

ts
// Contract:// - Receives a normalized transcript: the system prompt and tools live in//   the leading system message, never on the context itself.// - Must return an AssistantMessageEventStream.// - Direct streamSimple() calls may throw synchronously when request auth is//   missing. Once a stream is returned, request/model/runtime failures should//   be encoded in that stream.// - Error termination must produce an AssistantMessage with stopReason//   "error" or "aborted" and errorMessage, emitted via the stream protocol.export type StreamFunction<	TApi extends Api = Api,	TOptions extends StreamOptions = StreamOptions,> = (	model: Model<TApi>,	context: TranscriptContext,	options?: TOptions,) => AssistantMessageEventStream;

四条，逐条看。

第一条：收的是 TranscriptContext，不是 Context。 参数名叫 context 但类型是 TranscriptContext——只有 messages 一个字段。配合 2.1 的折叠，这意味着翻译器永远不会看到"独立的 systemPrompt"。

第二条：必须返回流。 不是 Promise，不是字符串，是 AssistantMessageEventStream。

第三条最容易被读错：

Direct streamSimple() calls may throw synchronously when request auth is missing. Once a stream is returned, request/model/runtime failures should be encoded in that stream.

它说的是分界线，不是"永不抛出"：

text
同步阶段（return 之前）        可以 throw    ← 鉴权缺失这类"根本无法开始"异步阶段（return 之后）        必须编码进流  ← 网络断、限流、模型崩

为什么这么分？因为同步抛出的错误调用方还没拿到流，只能 catch；而流已经返回之后，调用方已经在 for await 里了，再抛就没人接。分界线不是"错误类型"，是"调用方手里有没有流"。

实证在 anthropic-messages.ts:959-961：

ts

5.3 同一个契约，两种合规写法

回到 2.4 的差异：旧门面先 resolveApiProvider 再返回流，新入口先返回流再在 async 里解析 provider。

七、缓存：三种语义，四种实现

Agent 对话是有状态的：第 50 轮会把前 49 轮全发一遍。缓存就是告诉服务端"这段没变，别重算"。

抽象只有三个值（model-schema.ts:19）：

ts
export const CACHE_RETENTIONS = ["none", "short", "long"] as const;

但四家的"怎么标记"完全不同：

Provider short long 打在哪
Anthropic cache_control: { type: "ephemeral" } 加 ttl: "1h" system 块 + 最后一个 tool + 最后一条 user
Bedrock 插独立对象 { cachePoint: { type: DEFAULT } } 加 ttl: ONE_HOUR system 块后 + 最后一条消息后
OpenAI Responses 发 prompt_cache_key 加 prompt_cache_retention: "24h" 不打点，按 key 自动匹配前缀
OpenAI 兼容 照抄 Anthropic 的 cache_control 同上 同 Anthropic

四种思路，用一句话概括区别：

  • Anthropic 像贴便签：内容还是那些内容，附加一个"这段不变"的字段
  • Bedrock 像插路标：在消息流里插一个不含业务数据的独立对象
  • OpenAI 像报会员卡号：一个标记都不打，每次带个 key，后端自己算前缀重合
  • OpenAI 兼容厂商：直接抄便签协议

Anthropic 那条"三个位置"不是随便选的。实测代码（anthropic-messages.ts）：system 块在 :1225 / :1232 / :1241（三条 system 消息各打一个），最后一条 user/system 在 :1526-1547（注释就写着 Add cache_control to the last user or system message to cache conversation history），最后一个 tool 在 :1655——而且是只给最后一个：

ts
...(cacheControl && index === tools.length - 1	? { cache_control: cacheControl }	: {}),

为什么只给最后一个 tool？因为缓存按前缀匹配：把标记放在第 N 个 tool 上，等于声明"前 N 个 tool 都不变"。标在中间是浪费——请求最多 4 个断点，要用在覆盖范围最大的位置。

7.1 默认是 "short"，不是 "none"

这是最容易搞错的一条。anthropic-messages.ts:75-83：

ts

为什么会这样？因为不缓存纯亏：同一条系统提示词每轮重算一次，钱和延迟都翻倍。默认开是"防呆"，none 是给调试和对比实验留的开关。

顺带一个成本细节（models.ts:1247-1253）：1h 缓存写入按输入价的 2 倍计费。所以 long 不是无脑更省——短会话用 long 反而更贵。这是 CACHE_RETENTIONS 分三档而不是两档的原因。

7.2 这解释了 M03 的一个疑问

M03 说过："每轮都重建 llmContext，为什么不会破坏缓存？"

答案在这一节：缓存命中靠内容字节前缀匹配，跟你是第几轮调用无关。 只要 system 和 tools 的字节没变、标记位置没变，后端就能命中。重建数组不是问题，改内容才是。

而 2.1 的 timestamp: 0 正是为了让"每轮重建"产生字节完全一致的 system 消息。如果那里写成 Date.now()，缓存命中率会归零——一个看起来无关紧要的假值，是整条缓存链的地基。

8.8 为什么这一层不放进 ai

一句话：ai 是函数，这层是对象。

十、工程暗坑

1. partial 存数组会全部变成最后一次的状态。

ts
const frames = [];session.subscribe((e) => {	if (e.partial) frames.push(e.partial);   // ← 灾难});

所有元素指向同一个对象，最后全是终态。要存就存 { ...e.partial }，或者只存 e.type 和 e.delta。

2. done 有四个 reason，不是三个。

stop / length / toolUse / deferred。只处理前三个，遇到 deferred 会走进 default 分支。如果 default 里是 throw，那你就在"模型要求延迟"时崩了。

3. 同步抛出的错误不在流里。

streamSimple() 可能在 return 之前抛（鉴权缺失）。如果你只 for await 不 try，这个错误会直接冒到顶层。必须用 try 包住调用本身，而不只是包住循环。

ts
try {	const stream = streamSimple(model, context, opts);   // 这里可能抛	for await (const event of stream) { /* ... */ }} catch (err) {	// 两处都能接住}

4. thinkingLevelMap 的 null 不等于"没配"。

if (model.thinkingLevelMap?.[level]) 这种写法会把 null 和 undefined 一起判掉。看起来没差，但你在做"这个级别支持吗"的判断时，两者含义相反。

5. 缓存标记位置不是越多越好。

Anthropic 每请求最多 4 个 cache_control。超了会报错。coding-agent 只打三处是有原因的——留一个余量给调用方。

6. 长会话的 maxTokens 会被压到 1。

clampMaxTokensToContext 的下限是 MIN_MAX_TOKENS = 1，不是"至少给几百"。所以别把返回 1 个 token 当成 bug 报，它是"上下文满了"的信号。真正的修法是压缩（M09），不是调大 maxTokens。

7. await complete() 不抛错。

complete() = stream().result()，而 result() 在 error 事件上 resolve 的是那条错误消息。所以 try/catch 包 await complete() 只能接住同步抛出（provider 未注册、鉴权缺失），接不住网络错误。想统一处理，就得看 stopReason。

8. (string & {}) 不是笔误。

Api = KnownApi | (string & {}) 如果写成 KnownApi | string，那 KnownApi 就被 string 吃掉了，类型补全全失效。string & {} 的写法保留了字面量补全，同时允许任意字符串。

9. 离线构建里，目录数据是快照。

nix/model-catalog.json 钉着一份 model catalog 的 revision。Nix 构建没有网络， 所以内置的模型数据来自那个固定版本；运行时仍然用 pi.dev 的新数据覆盖。 快照负责"同样的源码构建出同样的字节"，覆盖负责"用户看到今天的模型表" ——两个都要，缺一个就变成"复现不了"或"新模型永远用不上"。平时 npm run build 会先刷新模型数据，npm run build:offline 不刷。

十一、三个可以带走的方法

方法一：用"折叠点"找设计的重心。

Context → TranscriptContext 的折叠只用一个二十四行的文件完成，但整个包的设计都围绕它：provider 只看 messages、工具集从 messages 算、压缩必须保住首条 system 消息、timestamp: 0 为了让字节可复现。

一个架构里真正重要的往往不是最大的文件，是数据类型转换发生的那几行。找到它，上下游就都通了。

方法二：契约里"能不能抛"要写清楚分界线。

StreamFunction 的注释不说"不抛异常"，而说"返回流之前可以抛、之后必须编码"。这句话的价值在于它明确了一个边界条件，而不是给了一个口号。

写任何 API 的注释时，问自己一句：这个"可以/不可以"是从哪个时刻开始算的？

方法三：把"支持程度"编码成三种状态，不要两种。

thinkingLevelMap 用 undefined / null / "high" 表示"默认支持 / 明确不支持 / 映射到某档"。如果用布尔值，你就表达不了"没表态"和"明确反对"的区别。

这条在配置系统里通用：默认值、显式覆盖、显式禁用是三种状态，不是两种。
