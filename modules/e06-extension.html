E06

写扩展 —— 三个钩子，一条看不见的消息

1,458 字 · 含 16 行代码 · 约 10 分钟

E05 加的是「模型能做的事」，E06 加的是「系统在什么时候做事」。

扩展不改工具列表，也不改循环。它只是注册几个函数，在特定时刻被调用： 工具调用前、工具结果回来后、每次请求模型前。听起来很轻，但 Pi 的文档 第一句就写清楚了：扩展跑在 Pi 进程里，权限和你一样。

三个问题：

  1. 一个扩展能看见什么，能不能改？
  2. tool_call、tool_result、context 分别在哪一刻触发？
  3. 为什么「只给自己看的消息」不能靠 display: false 过滤掉？

一、它是模块，不是插件包

一条扩展就是一个 TypeScript 文件，默认导出函数：

ts
import {  type ExtensionAPI,  isToolCallEventType,} from "@earendil-works/pi-coding-agent";export default function (pi: ExtensionAPI) {  pi.on("tool_call", async (event, ctx) => {    if (isToolCallEventType("bash", event)) {      console.log("bash:", event.input.command);    }  });}

放置位置决定它什么时候被加载：项目里的 .pi/extensions/、全局的 ~/.pi/agent/extensions/，或者临时用 pi -e ./path.ts 跑一次。

没有沙箱，没有权限声明。文档原话是它「能看提示词、工具调用、文件、凭据和 会话历史」。所以第一条规则不是「怎么写」，是「只装你读过的扩展」。

二、三个钩子：前、后、发之前

钩子 触发时刻 能做什么
tool_call 模型要调工具、还没执行 放行或 { block: true }
tool_result 执行完、消息落盘前 改结果（补丁式）
context 每次请求模型前 改这一轮要发的消息

tool_call 是最常见的权限闸门：命中危险命令就问一句，用户拒绝就返回 { block: true, reason }。

tool_result 是中间件：多个扩展按加载顺序跑，每个都能返回部分补丁 （content、details、isError 等），没返回的字段保持原值。注意一个 坑：改了 content 却不返回 structuredContent，结构化数据会被丢掉。

context 最像 E02 的闸门：

ts
pi.on("context", async (event, ctx) => {  const filtered = event.messages.filter((m) => !prune(m));  return { messages: filtered };});

event.messages 是不含系统消息的深拷贝，随便改。但有一件事它保证不了： 你把列表截短，Pi 仍会把当前的提示词段落和工具声明重新放到最前面。所以 「截断时别把提示词弄丢」不需要你操心，反过来也意味着你没法用这个钩子 删掉提示词。

三、一条看不见的消息

M06 讲过 Pi 的消息比模型能看的多四种。custom 是其中之一：

  • 它进 transcript，重启后还在；
  • 它有 display 字段，但那只控制「上不上屏」；
  • 它默认就不进请求。

很多人第一次会去找「让 custom 不进上下文的开关」，然后误把 excludeFromContext 当成它。那个字段属于 bashExecution 消息，不是 custom。custom 的隔离靠的是类型本身：投影函数只认四种消息，第五种 根本不在 Message 联合里。

那如果某条 bashExecution 不该进上下文呢？它的 excludeFromContext: true 就是干这个的。而如果你要按自己的规则剪枝，正确的位置是 context 钩子—— 它就是为「这一轮发什么」准备的。

三个地方，三种职责，别混：

需求 用什么
这条记录只给自己看 custom 消息
这条 bash 记录不进上下文 bashExecution.excludeFromContext
按规则裁剪这一轮消息 context 钩子

四、实验：三条日志，一次阻断

写一个 probe.ts，三个钩子各打一条日志：

  • 改哪里：.pi/extensions/probe.ts，三个 pi.on，每个一行 console.log。
  • 预期：一次工具调用会依次出现 tool_call、tool_result，下一次请求前 出现 context。
  • 连带：日志写 stdout 会污染 TUI 输出，调试时用 ctx.ui.notify 或写文件。
  • 回滚：删文件，或 /reload 前把文件挪走。

再加一条阻断规则：bash 命令含 rm -rf 时 return { block: true }。 判据是模型收到一条「被拒绝」的工具结果，而不是命令真的执行了。

本章实验未在本机跑通：pi-lab 依赖未装完（E04 §一）。 钩子名与返回结构抄自 docs/extensions.md，装好依赖后按上表验证。

五、小结

  • 扩展是进程内模块，权限等于 Pi，先信源后写码。
  • 三个钩子对应三个时刻：调用前、结果后、请求前。
  • display 只管上屏；excludeFromContext 只管 bash；裁剪用 context。
  • 日志别写 stdout，会污染 TUI。

六、概念回顾

概念 一句话 位置
ExtensionAPI 扩展拿到的句柄，pi.on 在它上面 core/extensions/types.ts
tool_call 执行前，可阻断 同上
tool_result 执行后，补丁式修改 同上
context 请求前，改消息列表 同上
custom 第五种消息，默认不进请求 core/messages.ts

七、练习

  1. （L2） 给 probe.ts 再加一条统计：一次会话里 tool_call 触发了几次。
  2. （L2） 用 tool_result 把超过 2000 字符的结果截断，并记录被截掉多少。
  3. （L3） 为什么 context 钩子里删掉的消息，不会导致提示词丢失？说出 Pi 在钩子返回后做了什么。
  4. （L4） 设计一个「写文件前必须确认」的扩展：用哪个钩子、怎么拿到路径、 用户拒绝时返回什么。写成一页报告。

八、三个常见误区

「扩展是沙箱里的，随便装。」 它和 Pi 同权限，能读凭据和整段会话。装之前先读源码，这是文档写明的第一条。

「用 display: false 就能让消息不进上下文。」 display 只影响渲染。是否进请求，取决于它的角色在不在 Message 联合里。

「tool_result 里改 content 就够了。」 省略 structuredContent 会让结构化数据失效，下游可能直接报错。

九、自检

  1. 三个钩子的触发顺序是什么？哪一个是「每次请求前」？
  2. custom 消息为什么不会进请求？是哪个开关在起作用？
  3. （L3） 为什么 context 钩子适合做「裁剪」，而 tool_call 不适合？

十、下一步：把六章连起来

到这里，Part E 的两段都走完了：

  • E01–E03：你自己造了一个 690 行的内核，知道每一层为什么存在；
  • E04–E06：你在真源码上改了值、加了工具、挂了钩子。

最后一件事不是写代码，是写一份报告：挑一个你真实的需求（比如「禁止 写入 .env」），说明你会用哪个钩子、改哪三个文件、怎么验证、失败怎么回滚。 报告里必须有一次真实运行记录；跑不通就写跑不通的原因，别编输出。

这份报告就是 L4 的判据：不是「你会写扩展」，是「你能判断该在哪一层写」。
