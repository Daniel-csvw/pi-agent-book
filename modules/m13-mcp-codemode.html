一、一次调用最贵的是什么

先不谈协议，看两个数字。

假设模型要做一件事：读三个文件、grep 一个符号、把那几处都改掉。用普通工具 调用，模型至少要走五轮循环： think → call read(a) → result → think → … → call edit → result。

每一轮的代价不是那一次工具执行，而是上下文里多出的四样东西：助手的调用 意图、参数 JSON、工具结果全文、以及下一轮模型必须重新读一遍的完整历史。

codemode 把这个过程压成一轮：

js
const a = await tools.read({ path: "a.ts" });const b = await tools.read({ path: "b.ts" });const hits = await tools.grep({ pattern: "loadConfig" });text(`a: ${a.length} chars, b: ${b.length} chars, hits: ${hits}`);

五轮往返变成一次往返。中间那两个文件的全文从来没进过上下文，只在沙箱的 堆里存在过。

这就是 coding-agent 里 codemode 工具的系统提示词说的那句：

Use codemode to batch independent tool calls (Promise.allSettled), chain them, or filter large output, instead of many separate calls.

（coding-agent/src/extensions/codemode/tool.ts:108-113）

二、MCP：一次会话的骨架

先对齐一个词：MCP 是什么

如果是第一次听这个词，先读这四段，后面会顺很多。

MCP = Model Context Protocol，一份开放协议，规定"Agent"和"工具服务器" 怎么说话。它不规定模型怎么想，只规定消息长什么样。

三个角色，各在一侧：

角色 在 pi 里是谁 干什么
host coding-agent 决定要连哪些 server
client packages/mcp 一次连接一个 server，管握手、请求、鉴权
server 外部进程或 HTTP 服务 报出自己有哪些工具，被调用时执行

协议上的能力原语有三个：tools、resources、prompts。pi-mcp 只实现了 前两个——client.ts 里有 listTools() 和 listResources()，protocol/types.ts 里也只有这两种的形状。没实现的那一个不影响读代码，但它提醒你：协议比实现大。

消息格式是 JSON-RPC 2.0，传输有 stdio（子进程）和 HTTP 两类，后者又分 streamable 与 SSE。§三 各有一节。

packages/mcp 的结构很干净，四层：

client.ts 的全部状态只有四个字（client.ts:41）： type ClientState = "idle" | "connecting" | "connected" | "closed";

2.1 版本协商：服务器说自己的，客户端负责接受

ts
// protocol/types.ts:4-10export const LATEST_PROTOCOL_VERSION = "2025-11-25";/** * Versions the client accepts from a server. Servers that do not support the * requested version answer with their own latest one, so older versions stay * accepted for servers built on older SDKs. */export const SUPPORTED_PROTOCOL_VERSIONS =  [LATEST_PROTOCOL_VERSION, "2025-06-18", "2025-03-26", "2024-11-05"] as const;

这段注释说清了 MCP 的版本规则：不是"客户端要求哪个版本就用哪个"，而是 客户端报一个，服务器可以回它自己的最新版。所以客户端要维护一个接受集合， 而不是比对相等。

client.ts:235-237 就是那个检查：

ts
if (!(SUPPORTED_PROTOCOL_VERSIONS as readonly string[])  .includes(result.protocolVersion)) {  throw new Error("MCP server selected unsupported protocol version "    + result.protocolVersion);}

一旦接受，就要把这个版本号回填给传输层（transport.setProtocolVersion?.()）， 因为 HTTP 传输每次请求都要带 MCP-Protocol-Version 头（§3.2）。

2.2 双向：客户端也可以是服务端

这是 MCP 和大多数 RPC 协议不一样的地方。看 McpClient 的两个字段：

2.4 超时、取消、和不许取消的那一个

请求的超时默认 30 秒（client.ts:38）： const DEFAULT_REQUEST_TIMEOUT_MS = 30_000;

但真正有意思的是超时和进度的关系。看 armTimeout 被调用的第二处：

ts
// client.ts:536-547private handleProgress(params: unknown): void {  if (!isObject(params) || !isJsonRpcId(params.progressToken)    || typeof params.progress !== "number") return;  const requestId = this.progressRequests.get(params.progressToken);  const entry =    requestId === undefined ? undefined : this.pending.get(requestId);  if (requestId === undefined || !entry) return;  this.armTimeout(requestId, entry);   // 收到进度就重新计时  try {    entry.onProgress?.(params as unknown as ProgressNotification);  } catch (error) {    this.emitError(error);  }}

进度通知会重置超时。否则一个跑了 5 分钟的构建工具，无论如何都会在 30 秒 时被客户端判死——即使它一直在报进度。这把"超时"从"总耗时"改成了"多久没 动静"，语义才对。

取消也有例外：

最后一个细节是 sendController：

ts

三、三种传输，一个接口

McpTransport 有七个成员，前六个必须实现，最后一个可选：

ts
// transports/transport.ts:18-26export interface McpTransport {  start(): Promise<void>;  send(    message: JsonRpcMessage, options?: McpTransportSendOptions,  ): Promise<void>;  close(): Promise<void>;  onMessage(listener: McpTransportMessageListener): () => void;  onError(listener: McpTransportErrorListener): () => void;  onClose(listener: McpTransportCloseListener): () => void;  setProtocolVersion?(version: string): void;}

send 收一个 JSON-RPC 消息，三个 on* 注册监听器并返回取消函数，close 关掉。所有"消息怎么变成字节"的差别，全在实现里。

3.1 stdio：换行就是帧

MCP 的 stdio 传输用 NDJSON——一行一个 JSON，没有长度头，没有分帧协议。

ts
// transports/stdio.ts:181-207private handleStdout(chunk: Buffer | string): void {  this.stdoutBuffer = Buffer.concat([this.stdoutBuffer,    Buffer.isBuffer(chunk) ? chunk : Buffer.from(chunk)]);  const maxMessageBytes =    this.options.maxMessageBytes ?? 三个容易被忽略的处理：

  1. 缓冲区无上限会 OOM：如果服务器一直不发换行、只发字节，indexOf 永远 返回 -1，stdoutBuffer 会一直长。所以超限就清空并报错——宁可丢一条消息， 也不要吃掉宿主的内存。DEFAULT_MAX_MESSAGE_BYTES = 16 MiB。
  2. \r 要剥：Windows 上的服务器会输出 CRLF（stdio.ts:199）。
  3. 空行要跳过，但要先 trim() 判断——有些服务器在启动时打 banner。

关停是一条三级阶梯（stdio.ts:152-179）：

ts

先关 stdin 让服务器自己退（500ms 宽限），然后 SIGTERM，再 2000ms 后 SIGKILL。 而且服务器退出后还要再杀一次进程树——因为 npx、uvx 这类包装器会留下 子进程。

killProcessTree 本身是一段平台差异的教科书（stdio.ts:17-41）：

3.2 streamable HTTP：一个端点，两种响应

这是 MCP 里最反直觉的一条设计：同一个 POST 端点，可能回 JSON，也可能回 SSE 流。

ts
// transports/streamable-http.ts:231-266async send(  message: JsonRpcMessage, { signal }: McpTransportSendOptions = {},): Promise<void> {  if (!this.started || this.closed) throw new McpConnectionClosedError();  const response = await this.authorizedFetch(    "POST",    {      headers: {        accept: "application/json, text/event-stream",        "content-type": "application/json",      },      body: JSON.stringify(message),    },    signal,  );  await this.checkResponse(response);  this.captureSession(response);  if (!isJsonRpcRequest(message)) {    // Notifications and responses are acknowledged with 202 and carry no    // reply; ignore any body.    await discard(response);    // The server-to-client stream may only open once the session is    // initialized.    const initialized = "method" in message      && message.method === "notifications/initialized";    if (initialized) this.startGetStream();    return;  }  if (response.status === 202 || response.status === 204) {    throw new McpHttpError(      response.status,      `MCP server accepted request ${message.method} without a response`,    );  }  const type = contentType(response);  if (type === "application/json") {    const body: unknown = await response.json();    const items = Array.isArray(body) ? body : [body];    for (const item of items) this.emitMessage(parseJsonRpcMessage(item));    return;  }  if (type === "text/event-stream" && response.body) {    void this.consumeResponseStream(response.body, message.id);    return;  }  await discard(response);  throw new McpHttpError(    response.status,    `Unsupported MCP response content type: ${type ?? Accept 头同时列了两种类型，服务器选一个回。三条分支各有其坑：

  • 通知（无 id）回 202、没有 body，直接丢弃。但 notifications/initialized 是个特殊时刻——它是"会话建好了"的信号，服务端到客户端的 GET 流只在这之后 才允许打开（streamable-http.ts:248）。
  • 请求回 202/204 是错误。202 的意思是"我收到了但没结果"，对一个请求来说 就是永远不会到来。
  • JSON 响应可能是单个对象，也可能是批处理数组（Array.isArray(body)）。

会话 ID 从响应头里捞（streamable-http.ts:334-337）：

ts
private captureSession(response: Response): void {  const sessionId = response.headers.get("mcp-session-id");  if (sessionId) this.sessionIdValue = sessionId;}

之后每个请求都带回去（buildHeaders，streamable-http.ts:325-332），同时带 上 MCP-Protocol-Version 和 Authorization。

404 的语义在这个协议里被重载了：

3.4 断流续传

服务器可以随意关闭一个响应流。如果它给了事件 ID，客户端就能续上：

ts
// streamable-http.ts:383-421private async consumeResponseStream(  body: ReadableStream<Uint8Array>, requestId: JsonRpcId,): Promise<void> {  const cursor: StreamCursor = {    lastEventId: undefined, retryMs: undefined, received: false,  };  let answered = false;  const onMessage = (message: JsonRpcMessage) => {    if (isJsonRpcResponse(message) && message.id === requestId)      answered = true;  };  let stream: ReadableStream<Uint8Array> | undefined = body;  let failure: unknown;  for (let attempt = 0; ; ) {    if (stream) {      try {        await this.consumeSse(stream, cursor, onMessage);        failure = undefined;      } catch (error) {        failure = error;      }    }    if (answered || this.closed) return;    if (failure !== undefined && !this.isRetryable(failure)) break;    if (cursor.lastEventId === undefined || attempt >= this.maxRetries())      break;    if (cursor.received) attempt = 0;    cursor.received = false;    const delay = this.reconnectDelay(attempt++, cursor.retryMs);    if (!(await this.sleep(delay))) return;    try {      stream = await this.openSseStream(cursor.lastEventId);    } catch (error) {      failure = error;      if (!this.isRetryable(error)) break;      stream = undefined;    }  }  if (this.closed) return;  const reason = failure === undefined    ? 这段里有四个决策：

  1. 没拿到事件 ID 就不重连（cursor.lastEventId === undefined）。没有 ID 就无法告诉服务器"从哪继续"，重来一次只能得到重复事件或丢失事件。
  2. 收到过事件就重置计数（if (cursor.received) attempt = 0）。一个能持续 吐事件的流，虽然断了，但它是健康的。
  3. 重连用 GET，不是重发 POST。工具调用可能已经执行了，重发就是重复执行。 所以续传是"继续收结果"，不是"重做请求"。
  4. 彻底失败时伪造一个 JSON-RPC 错误响应（最后那个 emitMessage），而不是 抛异常。因为 send 早已返回，只有一个假的 error 响应能让等待中的 pending 请求落定。

退避时间优先听服务器的：

ts
// streamable-http.ts:490-494private reconnectDelay(  attempt: number, serverDelayMs: number | undefined,): number {  if (serverDelayMs !== undefined) return serverDelayMs;  const initial = this.options.reconnect?.initialDelayMs    ?? isRetryable 有一处 Node 特有的判断（streamable-http.ts:483-488）：

6.2 沙箱防的不是恶意，是跑飞

一个脚本能做的事被限制到「调工具」，恶意空间几乎为零：它连文件都读不到。 真正的风险是另外两种。

第一种：跑飞。while (true) {} 或者一次算出 3 GB 的值。这不需要恶意， 模型写错一个循环条件就够了。

第二种：状态污染。上一次执行留下的全局变量、改过的内置对象、没关掉的 句柄，影响下一次执行。

两者的解法在 host.ts 的一句注释里：

一次执行一个 VM。不是「一个沙箱复用 VM」，是每次 execute() 新开一个 wasm 实例。代价是启动开销，换来的是：终止就是销毁，隔离不需要靠清理。

7.1 为什么参数和结果都是字符串

protocol.ts:4-8 的注释：

三个理由叠在一起：

  1. 跨越了三个边界：宿主线程 → worker 线程（postMessage）→ wasm 内存 → QuickJS 堆。「结构化克隆」只在第一个边界有效，后面两个都得手动搬运。
  2. 避免二次序列化：如果传对象，worker 要先 JSON.stringify 再塞进 VM；直接传字符串，VM 里的 JSON.parse 就是唯一一次解析。
  3. 桥的失败面变窄：字符串要么是合法 JSON 要么不是，没有「一个字段是 Map」这种中间态。

第 3 点不是理论。看 execution.ts:97-102：

if (this.finished) return 是所有竞态的收敛点。到期定时器、abort 监听、 VM 的 done、worker 的 crash——四路并发，都走这一个入口。

落定还有一个顺序要求：

（execution.ts:440-447）

先停 VM，再落定 Promise。反过来的话，调用方拿到结果就开始下一件事， 而 VM 还在跑——在那个空隙里它可能已经又发起了一次工具调用。

7.3 宿主侧的排队

通道是异步拿到的（launch 返回 Promise），但 VM 可能在拿到通道之前就发消息 了。所以有一个 unsent 队列（execution.ts:192-193），字段注释就是全部说明： private unsent: HostToWorkerMessage[] = [];

发消息的那三行是： if (this.channel) this.channel.post(message); else this.unsent.push(message);

通道到达时一次性冲掉（execution.ts:251-252）。这个队列在 finish() 里 会被清空——终态之后不再需要投递任何东西。

8.1 CodemodeSandbox：一个执行一个 worker

ts

SharedArrayBuffer(4) 是一个中断标志。为什么需要它？因为 terminate() 在某些运行时停不住一个卡在 wasm 里自旋的线程：

ts

所以停止是两步（host.ts:59-66）：

先竖旗（Atomics.store），再 terminate()，然后 unref() 让进程不必等它。 三步缺一不可：只 terminate 在 Bun 上停不住自旋；只竖旗在 Node 上要等太久； 不 unref 则一条跑飞的脚本能拖住整个进程退出。

这里还有一个 Node 的坑，写在消息监听里（host.ts:39-48）：

8.2 InlineCodemodeSandbox：和调用方共享一个线程

给没有 worker 的运行时用——Cloudflare Workers、浏览器。

问题写得很直白（inline.ts:5-9）：

QuickJS runs synchronously. While a script computes, the host's event loop does not run, so neither the deadline timer nor an abort signal can fire. On Workers even Date.now() is frozen during synchronous execution.

同步执行的 JS 期间，定时器、abort 信号、甚至 Date.now() 全部停摆。所以 「超时」在这个环境里根本不可用——超时检测器自己也在等待事件循环。

解法是中断预算：不按时间限制，按「被检查的次数」限制。

ts
// inline.ts:77-82shouldInterrupt: () => {  if (stopped || settled || exhausted) return true;  if (++polls <= interruptBudget) return false;  exhausted = true;  return true;},

QuickJS 会周期性地调用这个回调。数到第 interruptBudget 次就返回 true， VM 内部抛一个脚本捕获不到的中断。

默认值和实测速率都写在注释里（inline.ts:16-20）：

Measured with a tight loop: about 50,000 per second of CPU on an Apple M-series laptop and about 10,000 per second on Cloudflare Durable Objects (October 2026). The default of 100,000 allows roughly 2 to 10 seconds of uninterrupted computation; keep it well below the platform's own CPU limit, because hitting that limit resets a Durable Object instead of failing one script.

算一下：默认 100,000 次 ÷ 50,000 次/秒 = 2 秒（笔记本），÷ 10,000 次/秒 = 10 秒（Durable Object）。同一份预算，两种机器的实际时长差 5 倍。这就是 为什么它叫「预算」而不叫「超时」——它约束的是计算量，不是时间。

最后那句更关键：必须远低于平台的 CPU 上限。因为撞上平台上限的后果是 整个 Durable Object 被重置，而不是「这一个脚本失败」。一个脚本的错误 变成整个会话的故障。

栈大小也要跟着调（inline.ts:41-42）：

ts
/** Allows ~1,000 frames deep and trips before a 1 MB host stack overflows. */export const INLINE_MAX_STACK_SIZE = 256 * 1024;

worker 里用默认的 512 KiB（Node 的 worker 线程有 4 MB 栈），主线程只有 1 MB， 所以压到 256 KiB。QuickJS 的栈保护必须在宿主栈溢出之前触发——否则一个深递归 会直接杀掉进程，而不是抛出可捕获的 RangeError。

8.3 RemoteCodemodeSandbox：VM 在另一个 isolate

Cloudflare 上的正确做法。原因是一个实测数字（remote.ts:5-10）：

Measured on Cloudflare (October 2026), a script that computed for 10 seconds delayed the session's other requests by 10 seconds when it ran in the session object or in a Dynamic Worker, but by about 50 ms when it ran in a Durable Object of a separately deployed Worker.

10 秒 vs 50 毫秒，差 200 倍。同样叫「Durable Object」，部署在另一个 Worker 里才有隔离效果——同一个 Worker 里的不同 Durable Object 可能共用一个 isolate，也就是一条线程。

这也是 cloudflare.ts 里那句警告的由来：

（cloudflare.ts:42-49）

输出要攒。exchange 一次带一条调用，但输出可能是几百行，所以远端先攒：

停止只能靠回话。客户端无法中断一个正在计算的远端 VM：

9.1 lockdown()：冻结整个内置图

第一件事是把所有内置对象冻死。理由写在文件头（prelude-source.ts:30-32）：

注意这个理由和前文的 BridgeError 是同一件事：序列化代码和脚本在同一个堆。

但直接 Object.freeze 会遇到一个著名的陷阱：

text
// prelude-source.ts:51-57// Freezing alone breaks ordinary code through the "override mistake": a// data property that is read-only on a prototype cannot be assigned on an// instance either, so this.name = "MyError" in an Error subclass would// throw. 翻译一下：Object.prototype.toString 被冻结后，obj.toString = f 也会抛错 ——因为赋值会走原型的只读数据属性。而 class MyError extends Error { constructor() { this.name = "MyError"; } } 这种代码到处都是。

解法是把 7 个"常被覆盖"的属性从数据属性换成存取器：

js
// prelude-source.ts:59-61const OVERRIDABLE = new Set([  "constructor", "name", "message", "toString",  "toLocaleString", "valueOf", "toJSON",]);

  • 在原型自己身上赋值：抛错（"你不能改内置"）。
  • 在实例上赋值：定义成一个自有属性，合法。

一个 freeze 换成一个 defineProperty，语义上就等价于"只能遮蔽，不能修改"。 代价是每个属性多一层存取器，而收益是整个前奏不用再担心原型污染。

十、确定性重放

start() 这个名字很平淡，但它是两个包中唯一为"会话恢复"服务的机制。

10.1 问题是什么

Agent 在跑一段脚本，中途进程挂了。会话恢复后，这段脚本怎么接着跑？

两条路：

  • 重放工具结果。把已经发生的工具调用结果从日志里读出来，再往里倒。
  • 重跑脚本。让脚本从头再跑一遭，但这次工具调用不真执行，直接给记录的 结果。

第二条简单得多，前提是：脚本在相同输入下必须产生相同输出。而 JS 不是 默认确定的——时间、随机数、时区、GC 都能悄悄改结果。

10.2 四件事被钉死

vm.ts:23-36 把清单列了出来：

不确定性 怎么固定
时间 WASI 时钟读虚拟时间，从 startedAt 开始，只随 now 前进
随机 random_get 改走 seed 的 PRNG，不用真随机
时区 强制 UTC，timezoneOffset: 0
GC 不提供 WeakRef 和 FinalizationRegistry
投递顺序 结果带 seq，严格按序应用，早到的先缓冲

前四项靠 WASI 层和 Intrinsics 完成：

ts

第五项是整章最刺眼的一个细节：

ts
// vm.ts:107-115clock_time_get(  clockId: number, _precision: bigint, resultPtr: number,): number {  let nanoseconds: bigint;  // QuickJS seeds Math.random() from this reading in microseconds and  // turns 0 into 1, so seed s reads s + 1.  if (clock.creating) {    const seeded = BigInt(clock.seed + 1) * 1000n;    nanoseconds = clockId === 0 ? seeded : 0n;  }  else if (clockId === 0) {    nanoseconds = BigInt(Math.round(clock.now)) * 1_000_000n;  }  else {    nanoseconds =      BigInt(Math.round(clock.now - clock.startedAt)) * 1_000_000n;  }  new DataView(memory.buffer).setBigUint64(resultPtr, nanoseconds, true);  return 0;}

Math.random() 的种子是 QuickJS 从第一次读时钟的值里派生的。这意味着 "随机"和"时间"不是两个独立的不确定性，而是一个。所以创建上下文那一段 （clock.creating）必须读一个从 seed 派生的值——否则你发了 seed， 但 Math.random 根本没用它。

注释里还记了一个具体的坑：QuickJS 把微秒读数转成种子时，0 会被当成 1， 所以"种子 s 实际读到 s + 1"。这种偏移不写下来，以后没人能重现。

10.3 为什么结果要编号

因为跨进程传输不保证顺序。RPC 回复可能乱序到达，而脚本的语义要求"第 2 个 结果在第 1 个之后生效"。

ts
// vm.ts:210-223const { seq } = message;if (  seq === undefined || !Number.isInteger(seq)  || seq < nextSeq || early.has(seq)) {  throw new Error(    `Result ${message.id} has sequence number ${seq},`    + ` expected ${nextSeq} or later, once`,  );}early.set(seq, message);for (  let next = early.get(nextSeq);  next !== undefined;  next = early.get(nextSeq)) {  early.delete(nextSeq);  // Never backwards: a resumed host's clock may be behind the one that  // started the run.  if (next.now !== undefined && Number.isFinite(next.now)) {    clock.now = Math.max(clock.now, next.now);  }  current = nextSeq;  apply(next);  post({ type: "idle", seq: nextSeq, issued });  nextSeq++;}

两个约束：seq 不能重、不能回头；clock.now 只能增。后者是因为重放的 宿主时钟可能比原宿主慢——比如原进程在 10:05 挂掉，现在 10:03 重放。 时钟倒退会让脚本里的"耗时"变成负数。

七个成分：两个引擎版本、前奏的 FNV-1a 哈希、确定性协议版本、栈上限、堆上限、 中断预算。最后一个能影响结果——因为预算不同会让不同的脚本在不同点被中断。

DETERMINISTIC_VERSION 的注释把意图说得很清楚（vm.ts:65-69）：

Bumped whenever this module or the prelude changes what a deterministic script observes, beyond what the fingerprint's other parts (engine versions, prelude hash, limits) already capture.

它在说：指纹覆盖不到的东西，靠人手动报版本号。这是一个不得不接受的 漏洞，但至少它被写在了代码里。

10.5 during：脚本结束的那一刻在处理什么

确定性运行里有一个只有重放才关心的状态（types.ts:200-204）：

ts
/** In a start() run: the result the VM was processing when the script * first run, and the calls issued by then. */export interface CodemodeDuring {  seq: number;  issued: number;}

脚本可能在"处理第 3 个结果"的中途结束（返回、报错、exit()）。重放时必须 知道停在哪，否则下一次 deliver 会从错的位置接上。

这个信息藏在 done 里（vm.ts:278-293），因为当宿主收到 done 就会停掉 VM，那次 drain 的 idle 永远不会到达：

ts
case "done": {  // The host stops the VM on `done`, so the `idle` of this drain never  // arrives: report its numbers here.  const during = clock ? { during: { seq: current, issued } } : {};  ...}

一个"消息不会到达"的推理，换成一个字段。

十一、两条入口怎么接在一起

前八节讲的是两个包各自长什么样。现在讲 coding-agent 怎么把它们接起来。

11.1 四档暴露，默认是最省上下文的那档

MCP 服务器的 exposure 有四个值（coding-agent/src/core/mcp-servers.ts:52）： export type McpExposure = "codemode" | "deferred" | "direct" | "hidden";

每档的含义，mcp/index.ts:117-121 给了一行定义：

档位 模型看到什么 怎么调
direct 每个工具都是一条普通工具声明 直接调
deferred 不进声明，靠 tool_search 加载 加载后直接调
codemode 不进声明，只能从脚本里调 searchTools() 找，tools.x() 调
hidden 什么都不露 不可调

默认是 codemode（mcp/index.ts:135-137）： return entry.config.exposure ?? "codemode";

这个默认值很能说明设计取向。一个装了十个 MCP 服务器的人，如果默认 direct， 系统提示词里立刻多出百十来个工具定义；默认 codemode 则一条也不多——模型 只知道"有这么几个服务器，要用就写脚本"。

而且可以逐工具覆盖（toolExposure）。所以真实的配置可能是： 常用的那几个 direct，剩下几十个 codemode。

11.2 嵌套调用走同一条管道

这是两张图合成一张的地方。codemode 脚本调 tools.x() 时，不是直接调 工具对象，而是穿过 ctx.executeTool（codemode/execute.ts:540）： const outcome = await ctx.executeTool(tool.name, args, { signal: callSignal });

tool.ts:7-10 把后果说全了：

Scripts can call the agent loop's nested tools: active direct tools and every codemode or deferred tool. Nested calls run through the agent loop's tool pipeline (ctx.executeTool), so validation, tool_call/tool_result hooks, and permission checks apply exactly as for direct calls. Only the script's output reaches the model; nested results do not.

三句话，三个约束：

  1. 可调的范围：所有 direct（包括内置工具）+ 所有 codemode/deferred 工具。所以脚本里可以 await tools.bash(...)——但只有它自己被声明时。
  2. 同一管道：参数校验、tool_call/tool_result 钩子、权限检查，一条不少。 M05 里那句"否则权限检查就能被套一层工具调用绕过去"，在这里被落实了。
  3. 只有脚本输出进模型：嵌套结果全部留在沙箱里。这是整章的性价比所在。

11.3 一条结果里有一棵调用树

既然嵌套调用走管道，它们就会产生 tool_call / tool_result 事件。不加 处理的话，模型会看到"我调了一次 codemode，却产生了七次工具调用"的混乱 历史。

所以结果是嵌套的（codemode/tool.ts:88-106）：

ts
/** Tool call id of the nested call, `<codemode call id>/<n>`. */export interface CodemodeNestedCall {  id: string;  name: string;  args: string;  status: CodemodeNestedCallStatus;   // running | ok | error | cancelled  durationMs?: number;  error?: string;  cost?: number;}

id 的形式 "<codemode call id>/<n>" 是关键：它让一个嵌套调用既属于自己 （可单独引用），又属于父调用（可以整树折叠）。

M09 讲上下文压缩时提过一句"codemode 的嵌套调用也要算"。这里能看全： 成本、时长、错误、状态都记在嵌套节点上，但只有父调用的输出进上下文。

11.4 声明也要预算

direct 档也有代价：工具声明本身占 token。所以 codemode 工具的描述也是 有预算的（codemode/tool.ts:136-139）：

ts
/** Default for CodemodeDescriptionOptions.inlineBudget, in estimated * tokens. */export const DEFAULT_CODEMODE_INLINE_BUDGET =  SETTINGS_DEFAULTS.codemode.inlineBudget;/** Characters per token when estimating the cost of a tool section. */const CHARS_PER_TOKEN = 4;

默认是 3000，即约 12,000 字符的工具声明。超了就按"最便宜的优先"逐个 淘汰（tool.ts:197-200 的注释叫它 "like OpenCode's catalog"），没进目录的 工具依然可调，只是不再出现在声明里——模型的退路是 searchTools()。

同理，codemode/deferred 档的服务器需要专门告知存在。这就是 mcp_servers 系统提示词段（mcp/index.ts:190-221）。它的预算很硬：

ts
// mcp/index.ts:157-163const MAX_SERVER_DESCRIPTION_CHARS = 250;export const MAX_SERVERS_SECTION_CHARS = 4096;

4096 字符装下所有服务器，每个描述最多 250 字，装不下就截描述，再装不下就 把最后几个服务器折叠成一行"还有 N 个，用 searchTools() 找"。

十三、工程暗坑

1. Math.random 的种子是时钟读数的 +1。 vm.ts:107-115 注释里那句 "so seed s reads s + 1" 不是笔误：QuickJS 把 微秒读数当种子，还会把 0 当成 1。改 deterministicWasi 的返回值必须同步 改种子语义，否则 deterministic.test.ts 会挂在一个看起来无关的地方。

2. 中断有两个入口，不是一个。 interruptHandler: options.shouldInterrupt（vm.ts:170-179）由 QuickJS 在 字节码层调用；vm.ts:247 的 if (++jobs % JOBS_PER_POLL === 0 && ...) 是 宿主 drain 循环的兜底，管的是"脚本在等 promise、什么都不干"的那段时间。 只留一个，另一类跑飞就掐不住。

3. Bun 的 worker.terminate() 停不住在 wasm 里自旋的线程。 所以顺序是先置中断标志，再 terminate（host.ts:60-65）：

ts
Atomics.store(new Int32Array(interrupt), 0, 1);// A non-interruptible built-in can delay Bun's terminate() until it// returns (#10748).void worker.terminate().catch(() => undefined);worker.unref();

反过来写，那个线程会一直转到 wasm 自己退出。protocol.ts:35 把这句话 原样又说了一遍，因为它太容易写错。

4. terminate() 之后必须 unref()。 host.ts:64-65 的注释：terminate() 内部会让 worker 保持被引用，不 unref，主进程跑完不退出。这个 bug 的表现是"测试全绿，进程不结束"， 很难往沙箱上想。

5. Node 24/26 的 --watch 会污染 worker 的消息通道。 host.ts:40：--watch 把 watch:import / watch:require 混进 worker 的 message 事件（nodejs/node#65044），所以这里必须按形状过滤，而不是 按类型。只在开发模式复现的 bug，靠这段注释才追得回来。

6. guard() 必须放行 then 和 toJSON。 prelude-source.ts:233 那个判断里有三个成员是硬编码的。不放行 then， await tools.read(...) 在等待前会先读一次 tools.then，直接抛 "does not exist"——而用户的代码完全正确。

7. Cloudflare 里 fetch 不能直接当方法用。 streamable-http.ts:213 把 this.fetch 抽成一个包了一层的字段： (input, init) => fetch(input, init)。直接 this.fetch = fetch 会让 this 变成 auth context，Workers 报 "Illegal invocation"。这个错在本地 Node 里 永远不出现。

8. 401 之后的重试不会重发已经发出去的请求。 sendController 在请求落定时 abort（client.ts:582），而 transport.ts:9-16 的注释明说 "It does not undo a message already dispatched"。所以"刷完 token 重试"只对还没发的请求成立。幂等的读能 重试，写不能。

9. 会话过期和鉴权失败是两个错，处理方向相反。 404 + 有 Mcp-Session-Id 是 McpSessionExpiredError （streamable-http.ts:154），解法是换一个新 session 重来；401/403 是去 刷新 token。把它们合并成一个 "unauthorized" 会让两种恢复路径都失效。

10. 同一个 isolate 里的秒级脚本会卡住整个 Durable Object。 实测：10 秒的脚本，和请求共享 isolate 时延迟就是 10 秒；放进独立 Worker 的 DO，只多 50 ms。这是 remote.ts 存在的原因，也是"沙箱要不要独立部署" 这个问题的答案——看你的 CPU 预算愿不愿意和网络共享。

11. 16 MB 的上限是"累计持有"，不是"单条"。 MAX_OUTPUT_CHARS 限制的是脚本从开始到结束总共能产出多少，因为宿主一直 留着（prelude-source.ts:37-40）。一条 1 MB 的 text() 不违规，一百条 就违规。

12. stalled() 只在"没有 pending 调用"时成立。 prelude-source.ts:509-510 的第一行是 if (finished || pending.size > 0) return false;。所以脚本等一个永不返回 的工具调用时，这个检测救不了它——那要靠 execute() 的超时（默认 300 秒）。两个机制管两个方向，别指望一个。

十五、收束

15.1 三个可迁移的方法

一、"能力"和"编排"分开。 MCP 管能力怎么进来，codemode 管能力怎么被组合。两个包各自三千行上下， 因为它们只回答一个问题。写成一个包，就得同时背协议兼容和沙箱语义两套 复杂度。

二、沙箱的安全性来自"只有一条能力"，不来自"过滤了很多危险 API"。 codemode 脚本里没有 fetch、没有 process、没有 setTimeout（§6.1）。 它不是把危险的东西挑出来禁掉，而是只放进去一个 tools。前者是一张 永远补不完的黑名单。

三、要重放，就把不确定性一次性钉死，并留指纹。 时间、随机、时区、GC、投递顺序（§10.2），五个一起固定才有意义。固定完 还要报一个指纹（§10.4），因为"固定了"和"固定得一样"是两件事。
