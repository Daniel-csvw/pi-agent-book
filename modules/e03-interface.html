E03

接口 —— 先抽出来，再换一家模型

1,483 字 · 含 42 行代码 · 约 10 分钟

E02 结束时，loop.ts 还是写死的：createMockProvider()。想接真模型，按理 只该改一行。但大多数第一版做不到——它们把「发请求」写进了循环里，于是换 provider 等于重写循环。

这一章只做一件事：把 provider 抽成接口，然后证明它真的可换。

三个问题：

  1. 换一家模型，最少要改几行？
  2. 没有 key、没有网络时，怎么验证「换 provider 这条路是通的」？
  3. 你写的这 584 行，对应 Pi 的哪几处？
text
             loop.ts                |                |  只认 Provider 这个接口                v          +---- Provider ----+          |                  |   provider/mock.ts   provider/fixture.ts   provider/openai.ts     (假模型)          (回放 SSE)            (真 HTTP)

一、接口只有三样东西

<!-- file: examples/mini-agent/src/types.ts -->

ts
export interface Provider {  name: string;  stream(    messages: Message[],    tools: Tool[],    signal?: AbortSignal,  ): AsyncIterable<ProviderChunk>;}

messages 是历史，tools 是这一轮可用的工具，signal 是取消。三样缺一 不可，但也就这三样：

  • 没有 onText 回调——流式用 AsyncIterable 表达，调用方 for await 就行；
  • 没有 retry——重试策略属于宿主，不属于方言；
  • 没有 apiKey——凭据在构造 provider 时给，循环不该看见它。

接口越小，可换的空间越大。Pi 的 packages/ai/src/types.ts 里 Provider 也是这个形状，只是它多了一层「十种方言 → 统一事件」的翻译。

二、先写 fixture：不联网也能跑完整条路

真模型的问题不是难，是不可控。录一份 SSE 回复，按行重放，就能把「解析 + 翻译 + 进循环」这条路先跑通。

fixtures/openai-basic.jsonl 四行，最后一行是 [DONE]：

text
data: {"choices":[{"delta":{"content":"你好"}}]}data: {"choices":[{"delta":{"content":"，这是一份录好的回复。"}}]}data: {"choices":[{"delta":{},"finish_reason":"stop"}]}data: [DONE]

解析器要做三件事：拆掉 data: 前缀、跳过 [DONE]、把 delta.content 变成 text chunk。工具调用稍微麻烦一点，参数是分片到达的，要按 index 拼起来：

<!-- file: examples/mini-agent/src/provider/fixture.ts -->

ts
      if (call.id) slot.id = call.id;      if (call.function?.name) slot.name += call.function.name;      if (call.function?.arguments) slot.args += call.function.arguments;      pending.set(index, slot);

跑起来：

bash
node src/cli.ts --fixture "你好"

真实输出：

text
[turn 1] 你好，这是一份录好的回复。[stop]

关键不在「能输出」，而在它走的是和真模型完全相同的代码路径：同一个 loop.ts、同一个 toLlm、同一套事件。fixture 不是玩具，是回归测试的底座。

三、真模型只换三个值

provider/openai.ts 和 fixture 的差别，只有「数据从哪来」：

ts
  const env = process.env.OPENAI_BASE_URL ?? "";  const baseUrl = (options.baseUrl ?? env).replace(/\/$/, "");  const apiKey = options.apiKey ?? process.env.OPENAI_API_KEY ?? "";  const model = options.model ?? process.env.OPENAI_MODEL ?? "gpt-4o-mini";

同一个 stream 方法，前半段把消息转成供应商格式，后半段把 SSE 翻回 ProviderChunk。转换函数里最值得看的是 assistant 消息：

<!-- file: examples/mini-agent/src/provider/openai.ts -->

ts
      const calls = message.content        .filter((block) => block.type === "toolCall")        .map((block) => ({          id: block.id,          type: "function",          function: {            name: block.name,            arguments: JSON.stringify(block.args),          },        }));

这里有一个不可协商的细节：arguments 必须是字符串，不是对象。你在 自己的消息类型里存的是 Record<string, unknown>，到了线上要序列化一次； 读回来时再 JSON.parse 一次。忘了任何一次，接口都会报 400，而且错误信息 通常只说「invalid tool call」，不告诉你是哪一边。

凭据缺失时，它会立刻失败，而不是等 30 秒超时：

text
Error: 缺 OPENAI_BASE_URL 或 OPENAI_API_KEY

这是把「配置错误」和「网络错误」分开的最简单办法。

四、毕业判据：我的 584 行对应 Pi 的 9 处

到这儿，mini-agent 一共有 584 行源码 + 154 行测试。它当然不是 Pi，但它把 Pi 的骨架走了一遍。逐项对：

Pi 的 packages/agent/src 正好六个文件：agent-loop / agent / types / stream-fn / proxy / index。你写的七处，落在这六个文件加一个工具目录里。

「毕业」的标准不是行数，是这张表：随便指一处，你能说出它为什么在那， 以及少了他会坏在哪。 说不出来的那一行，回去重读对应章节。

五、五组实验

# 做什么 判据
1 --fixture "你好" 输出两行，[stop]
2 清空 OPENAI_API_KEY 再 --openai 立刻抛「缺 ...」
3 改 fixture 里的「你好」为「测试」 输出跟着变，循环代码一行没动
4 writeTool.execute({path:"tmp-w.txt",text:"hi"}) 返回 wrote 2 chars to tmp-w.txt
5 同一命令跑两次 输出逐字节相同

实验 3 是这一章的核心判据：数据变了，代码不用变。 如果你改一行 fixture 就要动循环，说明 provider 还没抽干净。

实验 5 证明 fixture 是可回归的：真模型做不到逐字节相同，录制回放可以。 这就是为什么 CI 里跑 fixture、不跑真模型。

六、小结

  • 接口三样：历史、工具、取消信号；其余都别进。
  • fixture 是为了让「换 provider」这条路离线可测，不是为了显得完整。
  • 真模型只差三个值：baseURL、key、model。
  • 毕业靠对照表，不靠行数。

八、练习

  1. （L2） 给 fixture 加一份带工具调用的录制，验证 toolCall 参数能拼完整。
  2. （L2） 把 OPENAI_MODEL 默认值改掉，确认请求体里的 model 跟着变（打印 body 即可）。
  3. （L3） 为什么 signal 要作为参数传给 stream，而不是在 provider 内部自己建 AbortController？
  4. （L4） 你要接一家返回 JSON（非流式）的供应商。说出最少要改哪几个文件、哪几个函数，以及为什么循环不用动。

九、三个常见误区

「fixture 是假的，测了不算。」 它测的恰恰是最容易出错的部分：分片拼装、finish_reason 映射、工具参数 序列化。真模型只会把这些错误放大，不会帮你发现。

「先接真模型，跑通再抽接口。」 跑通之后你就不想抽了，因为循环里已经混进了 URL、header 和重试。抽接口的 成本在第一周最低，之后每天都在涨。

「provider 应该自己处理超时和重试。」 超时属于调用策略，重试属于产品决策（要不要让用户看到重试）。放进 provider 之后，换个模型就得重写一遍策略。
