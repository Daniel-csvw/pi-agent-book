M09

上下文压缩 —— 两道闸门，两种摘要

11,593 字 · 含 1,034 行代码 · 约 60 分钟

M08 的最后一节说：每轮都要重算系统提示词。 原因是提示词依赖的工具集、目录、技能会变。

但还有一件事 M08 没提：重算的输入 messages 本身在变长。

用户问十句，模型跑二十次工具，messages 就有三十条以上。 每条工具结果动辄几千字符，一次 read 一整个文件就是上万字。 20 万 token 的窗口，撑不了多久。

撑不住的时候只有三条路：

  • 报错。把 400 甩给用户，让人自己想办法。
  • 静默截断。砍掉最早几条，假装没发生过。
  • 主动压缩。把旧历史改写成摘要，保留最近的原文。

Pi 走第三条，而且走得很认真：compaction.ts 1,105 行、 branch-summarization.ts 387 行、utils.ts 164 行，不到 1,700 行， 处理的是同一个问题——

当对话必须变短时，丢掉什么、记住什么、凭什么决定。

这一章拆这道题。两条线索：

  1. 普通压缩：同一个会话越跑越长，就地压扁。
  2. 分支压缩：会话在树上分叉，被放弃的那条路怎么留个念想。

两者共用摘要调用与文件清单，但四个地方全不一样： 切点算法、提示词、预算口径、摘要存放位置。 章末有一张逐项对照表。

先说读法，两分钟能省你两小时。这一章的代码密度是全书最高的一章： 10,100 字配 1,062 行代码，每千字 105 行，正好是全书均值（52）的两倍。 其中二十五处是节选——从 1,105 行的 compaction.ts 里摘几行。

所以读的时候记住三条：

  • 别指望把代码块拼回原文件。 节选只保留和论证有关的那几行。
  • 行号才是真坐标。形如 compaction.ts:412-470 的那串数字，去仓库里定位它， 不要按代码块的先后顺序找。
  • 真正的主线只有两条：在哪切（§四）和写什么（§五）。其余各节都是 这两件事的边角。

§十一 的七个实验都能照抄，其中实验 1 值得真跑：它让你亲眼看到一条 compaction entry 落在磁盘上长什么样。

零、读这章之前，你需要先知道一件事

compaction（压缩）：把旧对话压成一段摘要，用它顶替原来那一长串消息， 腾出上下文。它不是删除——原始 entry 还在会话文件里，只是不再进上下文： 像盖一张纸，不是撕掉。

没有它会怎样：以为压完历史就没了，不敢压；或者反过来，以为它能"清空"， 结果会话文件越压越大（M10 会看到那条 compaction entry 占多少字节）。

本书哪里用到：§二 两道闸门；§八 摘要怎么生效（CompactionEntry 的形状）。

这章怎么读：三条路线，按你现在要解决的问题选。

  • 只想知道"该不该压、压完会不会丢东西"→ §一、§二，二十分钟。
  • 要改压缩策略（切点、估算、模板）→ §三、§四、§五，再加 §八。
  • 要查证某个数字从哪来 → 直接跳 §十一 实验与章末源码索引。

一、压缩不是删除

1.1 磁盘上的历史一条都不能少

先排除一个直觉方案：既然太长了，就把前面的消息删掉。

做不到。原因不在模型，在存储。

session-manager.ts 的注释写得很直白：

ts
// session-manager.ts:1525-1531/** * Get all session entries (excludes header). Returns a shallow copy. * The session is append-only: use appendXXX() to add entries, branch() to * change the leaf pointer. append-only：只能追加，不能改、不能删。

这不是洁癖，是四个功能的前提：

功能 依赖
恢复会话 重放 JSONL 就能重建上下文
分叉（fork / tree） 每个 entry 有 parentId，靠链式指针回溯
审计 / 导出 发生过什么，文件里必须有
崩溃恢复 半截写入最多丢最后一行

如果压缩真的删了消息，上面四个全废。 所以压缩的做法是——在末尾追加一条"墓碑"，声明之前的不用看了。

1.2 一条 entry 代替一段历史

墓碑长这样（CompactionEntry）：

  • summary：改写后的摘要正文
  • firstKeptEntryId：从哪条开始保留原文
  • tokensBefore：压缩前多少 token
  • details：{ readFiles, modifiedFiles }
  • usage：生成摘要那次调用的 token 消耗
  • systemMessage：压缩瞬间的系统提示词快照

读上下文时，buildContextEntries 按这个规则筛：

ts

三步，值得逐句读：

  1. 沿当前叶子往上走，找最后一条 compaction，它自己排在结果数组首位。
  2. 从路径开头扫到 compaction 之前，只保留跨过 firstKeptEntryId 之后的， 且跳过 system 消息（提示词状态由 systemMessage 字段承担）。
  3. compaction 之后的所有 entry 无条件保留。

于是模型看到的是： 摘要 + 被保留的尾部原文 + 压缩之后继续发生的一切。

原始 JSONL 里那几千条消息还在，只是不再进入上下文。 换一个叶子读就是另一条分支的上下文——M10 展开。

1.3 三个必须守住的东西

墓碑方案要成立，切点就不能乱切。三条硬约束：

约束 违反的后果 谁来守
tool call 与 tool result 必须成对 Anthropic 等 provider 直接 400 isCutPointMessage 不允许切在 toolResult
保留区必须是"最近的" 模型丢掉刚做的事，重复劳动 从后往前累加 keepRecentTokens
摘要必须能"接着干" 摘要写成一本书的导读，模型不知道下一步 六节结构化模板 + 禁止续写

第三条最容易被低估。摘要不是给人看的总结， 是给另一个即将接手同一任务的模型看的交接单， 所以提示词里写着 another LLM will use to continue the work。

二、两道闸门

什么时候压？Pi 在两个位置各设一道闸门。

2.3 三种 reason

自动路径只有两种，加上手动一共三种：

reason 触发点 会重试原请求吗 失败文案
manual 用户 /compact、RPC、扩展 不会 Compaction failed: …
threshold 请求前 / 响应后超阈值 不会 Auto-compaction failed: …
overflow provider 报溢出或输出被截断 首轮会 Context overflow recovery failed: …

reason 会一路透传进事件（compaction_start / compaction_end / session_before_compact / session_compact / session_compact_failed）， 扩展据此决定显示什么、要不要插手。

2.4 溢出只赔一次

threshold 只是"快到线了，提前压"，压完继续跑，没风险。 overflow 是"已经撞墙了"——除了压，还得重放刚才那轮请求。 Pi 给这个重放只留一次机会：

三、token 从哪来

要判断"超没超"，先得知道"现在多少"。这一步没有完美答案，只能估。

Pi 用两级策略：有真实值就用真实值，没有就按字符数估。

3.1 第一级：provider 报回来的 usage

每次 assistant 消息都带 usage，四个字段：

3.4 chars/4 这条经验法则的两面

源码注释写着：

ts
// compaction.ts:294-297/** * Estimate token count for a message using chars/4 heuristic. * This is conservative (overestimates tokens). */

"conservative" 对英文和代码成立：BPE 词表下 4 个字符约 1 个 token， 实际往往更少，所以 /4 是偏高估。

但对中文不成立。一个汉字通常吃 1 个 token（部分模型 1.5–2 个）， 而 /4 只给它 0.25 个。中文长会话在这一步被低估到 1/4 甚至更低。

后果不是"多压一次"，而是"该压的时候没压"—— 第二道闸门看估算值没超线，请求发出去，provider 直接 400。

这是估算式方案的结构性缺陷，Pi 用两道闸门对冲： 请求前用估算，撞墙后用真实错误码兜底。

4.3 兜底是最后一个，不是第一个

六、split turn：串行的两份摘要

6.1 为什么必须分开

为什么必须分开？回到 §4.5 的三段结构。被切开的半轮有个尴尬的时间位置：

text
时间轴 ──────────────────────────────────────────→[主摘要区]        [turnPrefix 区]        [保留区]"很久以前"        "刚才这一轮的前半"     "现在的原文"

turnPrefix 区里的内容比保留区还早，但比主摘要区晚。 如果并进主摘要：

  • 叙述视角会乱——前面讲"上周做了什么"，突然接"刚才我在改第 3 行"。
  • 下次再压缩时，这段会被当成"历史"重新概括，正在进行的任务就变成了过去式。

并进保留区：又违背了"按 token 预算切"的原则——它可能很大，塞进去就超了。 所以单独一份，用专门的提示词。

6.2 三节模板

三节，比主摘要少一半。少了 Goal（有 Original Request）、 Constraints、Key Decisions、Critical Context。 因为读者马上就要拿到后半段的原文，不需要提前知道最终目标。

最后一句是防幻觉的关键：

模型拿到的只有前半轮，它天然想"补全"后面发生了什么。 这句话把它按回去：只写你看见的。

6.3 串行，不是并行

这里要纠正一个很自然的猜测：两份摘要是不是 Promise.all 并行跑？

不是。

  2. 限流。压缩本身高频，同时发两份会翻倍触发 RPM 限制，还把重试搞复杂。
  3. 顺序即语义。先"历史讲完了"，再"接着这一轮"，串行写在代码里， 读的人也顺着这个顺序理解。

注意 let historyText = previousSummary ?? "No prior history."; ——若 messagesToSummarize 为空且没有上一版摘要，主摘要位置就写这个占位。 否则合并后开头是 \n\n---，模型可能把它当成"上面被截断了"， 然后开始道歉或补全。一个 16 字符的占位，省掉一次幻觉。

7.1 三个集合

摘要是有损压缩。写得再好也会丢细节， 但有一类丢了会直接导致返工：动过哪些文件。 所以 Pi 单独抽一层，边扫描边记账：

7.4 readFiles 是「只读未改」

8.5 压缩完还是超怎么办

没有任何机制保证"压完一定不超"。可能的结果有三种：

九、分支摘要：另一条完全不同的路

9.1 场景

用户在 /tree 里退回到三小时前，选了一条岔路。 原来那条路上的二十次工具调用、四次失败尝试、最终找到的那个 bug—— 全在废弃分支上。但那个 bug 的结论对现在有用。

十二、工程暗坑

这些坑的共同点：代码不报错，行为悄悄错。

12.1 chars/4 对中文严重低估

§3.4 讲过。后果是"该压没压"，撞到 provider 400 才补救。 中文为主的 agent 应把系数改成 /2 或按 tokenizer 实测。

12.2 图片固定 1,200 token

ESTIMATED_IMAGE_CHARS = 4800 除以 4。一张 4K 截图和图标算出来一样。 多模态长会话里误差会累积成"估算说还有 3 万，实际已经爆了"。

12.3 摘要模型会"顺手整理"路径

模板里写了 Preserve exact file paths，仍然会丢。 真正保险的是 details 里的结构化清单 + 代码外挂的 <read-files> 块。 能外挂的别让模型复述。

12.4 thinking 被丢掉，等于丢掉推理链

对推理型模型，thinking 往往是"为什么这么改"的唯一记录。摘要里没它， 接手模型只能看到"改了什么"。源码的理由（避免摘要请求比被摘要内容还大） 站得住脚，但需要推理链的场景应该在 customInstructions 里显式要求。

12.5 length 停也要当失败，否则半截摘要进会话

放过 stopReason === "length"，会话里就会出现一个写完 ## Goal、 ## Progress 就断掉的摘要。它看起来完全正常，模型照着它继续—— 但 Next Steps 根本没生成。

12.6 溢出只赔一次，第二次直接放弃

_overflowRecoveryAttempted 是实例字段，不清零。 一个长会话里已经救过一次，第二次溢出就是硬失败（得换会话或换模型）。

12.7 换模型后旧溢出标记会误触发

_modelForMessage 找不到产出这条消息的模型时，sameModel = false， 溢出检查整段跳过。这是保护，也是盲区： 如果模型真的没了（配置删了），溢出永远不会被恢复。

12.8 压缩刚结束，第一轮又触发

因为保留区里的 usage 是压缩前的，assistantIsFromBeforeCompaction 用时间戳挡住。自己写类似机制时，用时间戳比，而不是比"是否在保留区"—— 保留区里的消息可能比 compaction entry 还新。

12.9 手动压缩会打断正在跑的 turn

compact() 第一行就是 await this.abort()。 扩展或脚本在模型输出中途调它，那次输出直接作废。 要"压完接着跑"，得自己记住上下文再重发。

12.10 扩展接管压缩时，文件清单可能为空

session_before_compact 返回 { compaction } 时，details 由扩展自己给。 不给就是 undefined，下游拿到的 readFiles / modifiedFiles 全空。 fromHook: true 就是这个来源的标记。

12.11 分支摘要的 90% 保底可能仍然超预算

那个分支只在 totalTokens < tokenBudget * 0.9 时塞入， 但塞进去的那条摘要本身可能就有 5 万 token。 结果总量超预算，请求被 provider 拒绝。极端情况需要扩展在 session_before_tree 里自己接管。

12.12 分支摘要跳过 toolResult，可能丢掉关键证据

getMessageFromEntry 对 toolResult 返回 undefined。 如果那条支线的价值恰恰是"某条命令的输出证明了根因"，这段证据不会进摘要。 需要就在 customInstructions 里明说，或让扩展接管 summary。

十三、三个可以带走的方法

13.1 用「追加墓碑」代替「原地删除」

只要存储是 append-only 的，任何"删除"都能表达成"追加一条声明"。 compaction entry 就是这个模式： 一条 entry 说"从这里往前别看，看我的 summary，从 firstKeptEntryId 起恢复原文"。

好处不只是可回滚。更关键的是同一份历史可以有多个视图—— 不同叶子读同一份 JSONL 得到不同上下文（M10 的分叉靠的就是这个）。

13.2 估算要两级：可信锚点 + 增量外推

estimateContextTokens 的骨架值得抄：

  1. 找一个可信锚点（provider 真实报回来的 usage）。
  2. 只对锚点之后的增量做估算。
  3. 锚点失效时（被 edit / compaction 改过）整体重估，别硬用。

纯估算会累积漂移，纯真实值又拿不到（成本、延迟），两级混合最省事。 第三点是关键：把"锚点可能已经失效"写进结构（lastUsageIndex: null）， 而不是靠调用方自觉。

13.3 摘要要写成「交接单」，不是「读后感」

三条硬要求：

  • 结构化。六节固定标题，缺一节模型就少一个抓手。
  • 禁止续写。模板 + 系统提示 + 拍平输入，三重保险。
  • 可丢弃。tools do not call / length 即失败， 宁可整次压缩失败，也不接受一份"看起来完整"的残缺品。

最后一条最容易被忽略：压缩失败的成本是一次模型调用， 而残次摘要的成本是接下来几十轮都在错误的前提下工作。差两个数量级。

十四、压缩没生效时，先查这四件事

一，配置被上层覆盖了。 压缩配置三层解析：模型覆盖 > 全局 > 默认 （settings-manager.ts 1,457 行）。先看 modelOverrides 里有没有你忘了的那一项。

二，阈值算错了。 阈值 = 上下文窗口 − reserveTokens。 reserveTokens 调得过大，就会出现"还没装满就压"。

三，锚点失效了。 历史被 edit 或上一次压缩改过之后，估算必须整体重算， 不能继续用旧 usage 往后外推（§三 的 lastUsageIndex）。

四，摘要被拒了。 length 即失败、tools do not call——宁可整次失败， 也不接受一份残缺摘要（§13.3）。四件都排查完还没压，大概率是闸门根本没被调到： _exceedsCompactionThreshold 返回 false 时，两道闸门都在等下一轮。

本章小结

  1. 压缩不是删除，是追加一条 compaction entry 当墓碑。
  2. 两道闸门：请求前预判（threshold）、响应后溢出（overflow）。
  3. 切点从后往前累加；兜底取最后一个，不是第一个。
  4. token 估算两级：可信锚点 + 增量外推，锚点失效就整体重估。
  5. 摘要写成交接单：结构化、禁续写、可丢弃。

练习

练习 1（读）：§二 说两道闸门一前一后。 如果把 overflow 那道关掉，什么情况下会先崩？ → 回 §二 的两道闸门与 M03 §十 的失败路径。

练习 2（改）：照 §十一 实验 7 把 reserveTokens 设为 1， 并注释掉 _runAutoCompaction("threshold", false)。 预期：reason 从 threshold 变成 overflow；回滚：二者都恢复原样。

常见误区

  1. 你会以为 压缩后原文就没了；实际是 摘要 + firstKeptEntryId 之后的原文都在； 证据 §一、§八。
  2. 你会以为 摘要越短越好；实际是 缺一节就少一个抓手； 证据 §五 的六节模板。
  3. 你会以为 压缩失败很严重；实际是 失败只花一次调用，残次摘要拖几十轮； 证据 §13.3。
