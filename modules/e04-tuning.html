E04

调参 —— 先改一个数字，再谈改代码

1,963 字 · 含 12 行代码 · 约 11 分钟

前半结束在 E03 的对照表上。从这一章开始，你不再写自己的内核，而是进 pi-lab/ 改 Pi 本身。第一个动作不是读代码，是确认你改的是能跑的那份。

这一章的所有实验都只改值和配置，不动一行逻辑。目的很单纯：让你先体会 「行为是参数决定的」这件事，再决定要不要动代码。

三个问题：

  1. 不改代码，能改变 Pi 的哪些行为？
  2. 六个旋钮里，哪个最容易被忽略、后果却最大？
  3. 改坏了怎么回去？没有 git 的副本怎么回滚？

一、先过四道闸

pi-lab/ 是 pi-main/pi-main 的副本，版本必须一致。动手前跑：

bash
node scripts/lab-check.mjs

我本机的真实输出（网络受限，依赖没装完）：

text
[PASS] node     24.12.0[PASS] 副本版本     1.4.0（与 pi-main 一致）[PASS] 依赖       node_modules 已就绪[FAIL] 可启动      exit 1[INFO] 未发现模型凭据；离线实验不需要，接真模型时再配

第 4 条失败的原因不是版本，是依赖树不完整：

text
Error: Cannot find package  '.../pi-lab/node_modules/cross-spawn/index.js'

npm install --offline 只装了一半。这不是 Pi 的问题，是网络的问题。判据 的作用就在这里： 它不让你在「副本是坏的」情况下改配置，然后把失败归因 给参数。

一条命令修：

bash
cd pi-lab && npm install

装完再跑一次，第 4 条应该变成：

text
[PASS] 可启动   1.4.0

二、六个旋钮

# 旋钮 改哪里 你会看到什么
1 图片进不进上下文 设置项 blockImages 粘贴截图后模型还能不能描述它
2 思考档位 设置项 thinkingLevel（七档） 同一问题的推理长度与花费
3 换模型/换供应商 models.json 模型列表、默认模型、能力标记
4 系统提示词删一段 sections 里删一个 key 行为变化，且能定位到哪一段
5 输出上限的安全边距 simple-options.ts 长回答被截断的时机
6 压缩触发点 压缩阈值 什么时候开始摘要、摘要几次

六个别急着全改。按「改动成本」排序：1、2、3 是配置，4 是调用方，5、6 才是源码常量。先做前三个，你会对「参数决定行为」有体感；再做后三个， 才知道该在哪里加日志。

三、三个配置旋钮：四行格式

每个实验固定四行：改哪里、预期、连带、回滚。

旋钮 1：blockImages

  • 改哪里：用户设置文件里加 "blockImages": true。
  • 预期：粘贴图片后，请求里不再带 image 内容块；模型只能说「我看不到图」。
  • 连带：settings-schema.ts 会校验类型；写成字符串会被拒绝。
  • 回滚：删掉这个 key，或改回 false。

Pi 有一个专门的测试文件 packages/coding-agent/test/block-images.test.ts。 它证明的不是「图片能不能显示」，而是「内容块有没有被拦在请求之前」。这就是 配置项的边界：它在消息组装之后、provider 之前生效。

旋钮 2：thinkingLevel

  • 改哪里：设置里把 thinkingLevel 从默认档改到最高档。
  • 预期：同一个问题，assistant 消息里的 reasoning 段更长，耗时和花费上升。
  • 连带：不同模型支持的档位不同，simple-options.ts 里有 clamp 逻辑， 超档会被压回去，而不是报错。
  • 回滚：改回原档位；记下改之前的值。

七档不是「越多越好」。它是给不同预算的人留的刻度：写代码要中档，做摘要 要低档，解难题才用最高档。E06 的扩展里如果自己调模型，也要传这个值。

旋钮 3：models.json

  • 改哪里：换一条 provider 记录，或改默认模型的名字。
  • 预期：--version 不变，但模型列表与默认选择变了；启动时能看到新模型。
  • 连带：能力标记（上下文窗口、是否支持工具）必须跟着改，否则请求会被 供应商拒绝，而 Pi 只报一个笼统的 400。
  • 回滚：先把原文件复制成 models.json.bak，改坏了覆盖回去。

这条最容易出错的地方不是 JSON 语法，是能力标记和真实模型不匹配。 窗口写大了，压缩永远不触发；工具标记写错了，模型永远不调工具。

四、三个源码旋钮：改常量，不改结构

旋钮 4：删一段系统提示词

packages/coding-agent/src/core/system-prompt.ts 里，提示词是按 sections 拼的：

ts
  /** Additional XML-wrapped prompt sections keyed by tag name. */  sections?: Record<string, string>;

删掉一个 key，对应那一段就不进提示词。注意是删 key 或传 undefined， 不是传 null——类型是 Record<string, string> | undefined，多传一个 null 只会在拼字符串时变成 "null"，看起来没坏，实际污染了提示词。

判据：删掉工具说明那一段后，模型开始用错工具参数。这说明提示词和工具 schema 是两套东西，缺一不可。

旋钮 5：输出上限的安全边距

packages/ai/src/api/simple-options.ts 里有一层 clamp：请求的 maxTokens 不能超过「上下文窗口 - 已用 - 安全边距」。把边距改小，长回答更容易被截断； 改大，留给输入的空间更少。

这条实验的价值在于让你看到 stopReason: "length" 是怎么产生的：不是模型 不想说，是预算到了。

旋钮 6：压缩阈值

packages/coding-agent/src/core/compaction/compaction.ts 里，触发压缩的判断 依赖 tokensBefore。把阈值往下调，你会更早看到摘要；往上调，摘要变少但 单次请求更贵。

判据不是「有没有摘要」，而是摘要之后第一轮的回答是否还接得上。接不上， 说明阈值不重要，摘要内容才重要——这正是 M09 的主题。

五、六组实验

# 做什么 判据 回滚
1 跑 lab-check 四条全 PASS 才继续 无
2 blockImages: true 请求里没有 image 块 删 key
3 思考档位调到最高 reasoning 变长、耗时上升 改回原值
4 改 models.json 的默认模型 启动后默认模型变了 覆盖 .bak
5 删 sections 一个 key 行为变化，工具参数开始出错 恢复 key
6 压缩阈值减半 更早出现摘要 改回常量

第 1 组是前置条件，不是实验。没跑通第 1 组之前，后面五组的失败都没有 解释力。

六、小结

  • 配置旋钮改的是「请求长什么样」，源码旋钮改的是「什么时候发」。
  • 六个旋钮里，models.json 的能力标记最危险：错了不报错，只是行为怪。
  • 回滚靠 .bak，不靠记忆。副本没有 git，删了就没了。
  • 判据要能一句话说清，否则你只是在「感觉不一样」。

七、概念回顾

概念 一句话 位置

thinkingLevel 七档，超出会被 clamp ai/src/api/simple-options.ts

tokensBefore 压缩触发的依据 core/compaction/compaction.ts

八、练习

  1. （L2） 把 thinkingLevel 改到最高档，记录同一问题的耗时与花费，和默认档对比。
  2. （L2） 故意把 models.json 的上下文窗口写大 10 倍，观察压缩还会不会触发。
  3. （L3） 为什么 blockImages 放在「组装后、请求前」最合适？放在 provider 里会多出什么代价？
  4. （L4） 你要让 Pi 默认不加载图片，但保留「用户显式要求时能加载」。说出改哪个旋钮、加什么条件，以及为什么不该改源码。

九、三个常见误区

「配置改完重启就行，不用验证。」 models.json 的能力标记错了不会报错，只会让行为变得奇怪。每次改完都要跑 一次最小请求，看 stopReason 和 token 用量。

「思考档位越高越好。」 高档位在简单任务上只会更慢更贵，还更容易过度推理。档位是预算刻度，不是 质量开关。

「副本坏了，重新复制一份就行。」 复制一次要好几分钟，而且会把你改过的文件一起覆盖。正确做法是改前 .bak， 改后一条 cp 回滚。

十、自检

  1. 说出六个旋钮里哪三个是配置、哪三个是源码。
  2. sections 传 null 会发生什么？为什么类型系统救不了你？
  3. （L3） 如果 models.json 把上下文窗口写小了，你会先看到什么现象？为什么 不是「请求报错」？
