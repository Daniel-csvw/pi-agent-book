E05

加工具 —— 从契约到渲染，一个新能力

1,533 字 · 含 17 行代码 · 约 10 分钟

E04 只改值和配置，模型能做还是那些事。想让它多一种能力，必须加工具。

加工具听起来像「写个函数」，实际要动的地方比你想的多：模型得知道它存在、 知道什么时候用、参数怎么填；用户得看见它在跑、跑完是什么结果；失败时 两边都要收到干净的错误。

这一章以 outline 为例（列出一个文件的函数/类/导出），把五个落点走一遍。

三个问题：

  1. 一个工具在 Pi 里到底由几部分组成？
  2. 参数 schema 写在哪，谁在用它？
  3. 工具失败了，模型和用户各自看到什么？

一、一个工具，五个角色

以 read 为例，同一个能力在不同层出现五次：

角色 在哪 谁看
参数 schema read.ts 的 readSchema 模型填参数
提示词贡献 readToolSystemPromptContribution 模型判断该不该用
定义/执行 createReadToolDefinition 循环调用
注册汇总 core/tools/index.ts 宿主组装工具集
渲染 renderers/read.ts 用户在 TUI 里看到

少任何一处，能力都是残的：没有 schema 模型不会填参数；没有提示词贡献， 模型不知道有这么个工具；没有渲染，用户只能看到一坨 JSON。

二、schema：模型唯一的说明书

packages/coding-agent/src/core/tools/read.ts 开头：

ts
const readSchema = Type.Object({  path: Type.String({    description: "Path to the file to read (relative or absolute)",  }),  // 另有 offset / limit 两个可选字段，各带一句 description});

三个字段，两个可选（排版时折了行，字段没变）。注意每个字段都有 description——它会被原样塞进请求的 tools[].function.parameters，模型 就是靠这几句话决定传什么。

你的 outline 只需要一个 path。能少一个字段就少一个：字段越多，模型 填错的概率越高，而错误参数会让整个工具调用失败。

三、提示词贡献：让模型知道「什么时候用」

schema 只说明「怎么填」，不说明「什么时候用」。后者由一段独立的贡献文本 负责：

ts
export const readToolSystemPromptContribution = {	snippet: "Read file contents",	guidelines: ["Use read to examine files instead of cat or sed."],} as const;

snippet 是一行简介，guidelines 是使用规则。它们会被拼进系统提示词的 工具段。E04 的旋钮 4 删掉这段，模型就会开始用 bash 去 cat 文件——不是 它不聪明，是没人告诉它别这么做。

outline 的贡献应该写清楚边界：「只在需要结构而不是全文时使用」。

四、注册：两种形态，一个来源

core/tools/index.ts 里，每个工具都导出两个东西：

ts
export {	createReadTool,	createReadToolDefinition,	type ReadToolDetails,	type ReadToolInput,	type ReadToolOptions,} from "./read.ts";
  • createReadToolDefinition(cwd, options) 给需要完整定义的调用方；
  • createReadTool(cwd, options) 给「只用执行」的场景。

两者都从同一个 read.ts 出来，不存在两套逻辑。这就是「一个工具一个 文件」的价值： 加工具只加文件，不改老文件。

outline 照做：新建 outline.ts，导出 createOutlineTool 与 createOutlineToolDefinition，再在 index.ts 补一行导出、在工具集组装处 补一行注册。

五、执行：截断和队列，两个必踩的坑

read 的返回值不是「文件全文」，而是截断后的结果。truncate.ts 里有两个 默认值：DEFAULT_MAX_BYTES 和 DEFAULT_MAX_LINES。超过就截，并把截断 信息放进 details。

原因很直接：工具返回值下一轮就进上下文。一个 200KB 的日志能让这一轮直接 超预算，而模型看到的东西和「文件不存在」几乎没有区别。

第二个坑是写。outline 只读，不涉及；但你要加 write/edit，就必须走 withFileMutationQueue（同目录的 file-mutation-queue.ts）。M05 §五 讲过 为什么：两个并发写同一文件，锁必须加在「读-改-写」整段外面，加在函数 入口等于没加。

六、实验：加一个 outline

步骤固定四行格式：

  • 改哪里：新建 core/tools/outline.ts（约 40 行），index.ts 补导出与注册。
  • 预期：启动后工具列表里出现 outline；模型对「这个文件有哪些导出」 这类问题会选它。
  • 连带：renderers/outline.ts 可以先用默认渲染；提示词贡献必须补，否则 模型不会主动用。
  • 回滚：删文件 + 撤两行注册；或从 .bak 覆盖 index.ts。

判据三条，缺一不可：

  1. 工具列表里有它（用户可见）；
  2. 模型能正确填 path（schema 生效）；
  3. 结果在 TUI 里不是一坨 JSON（渲染生效）。

第 2 条最容易假通过：工具被调用了，不代表参数对。看 tool_call 事件里的 input，不要只看「有没有输出」。

本章的实验未在本机跑通：pi-lab 的依赖没装完（见 E04 §一）。 命令与判据来自 read.ts / index.ts 的真实结构，装好依赖后按上表验证。

七、小结

  • 一个工具五个角色：schema、提示词贡献、定义、注册、渲染。
  • schema 是模型唯一的说明书，字段越少越好。
  • 提示词贡献决定「会不会被用」，schema 决定「填得对不对」。
  • 读取必须截断，写入必须排队。

九、练习

  1. （L2） 把 readSchema 的 limit 改成必填，观察模型在没给行数时怎么填。
  2. （L2） 给 outline 加一个 depth 参数（1 只列顶层，2 含嵌套），只改 schema 和实现。

  4. （L4） 你要加一个 write 工具。列出必须改的五个落点，并说明并发锁加在哪一层、为什么。

十、三个常见误区

「工具就是个函数，注册一下就行。」 漏了提示词贡献，模型不会用；漏了渲染，用户看不懂；漏了截断，上下文会炸。

「参数校验交给运行时，schema 写宽松点。」 schema 是模型唯一的约束。写宽松，模型就会传 limit: "10" 这种字符串， 然后你在 execute 里补一堆 Number()。

「失败就返回一段错误文本。」 错误文本会被模型当成正常结果继续推理。要让它进入 isError 分支，模型才 知道「这条路走不通」。

十一、自检

  1. 说出 read 的五个落点，以及少一个会坏在哪。
  2. createReadTool 和 createReadToolDefinition 为什么要同时存在？
  3. （L3） 如果 outline 的提示词贡献写成「读取文件结构」，模型可能会在什么 场景误用它？你会怎么改写这句？

十二、下一步

工具是「模型能做的事」，扩展是「系统在什么时候做事」。两者都能改行为， 但扩展不改工具列表，它挂在生命周期上。
