四、锁：一条 promise 链

ts
const prev = locks.get(key) ?? Promise.resolve();const next = prev.then(fn, fn);locks.set(key, next.catch(() => {}));return next;

四行，值得逐行读。

prev 是「这个 key 上一次的任务」。 第一次调用时没有，就当成「已完成」。

prev.then(fn, fn) 里的两个 fn：成功也执行、失败也执行。如果写成 prev.then(fn)，前一个写失败之后链就断了，后面的写永远不跑——你会看到「文件 没生成，也没有报错」，这是最难查的一类问题。

locks.set(key, next.catch(() => {})) 存的是「吞掉异常后的版本」。 目的是 让链不断，同时不制造 unhandled rejection。return next 返回的才是带异常的 原版，所以调用方仍然能拿到错误。

为什么要 .catch 而不是 .finally？ finally 会把值也吞成 undefined， 下一环拿不到结果；我们只需要「错误不阻断链条」，不需要改结果。

再看实验数据：

text
不加锁: A@47ms C@47ms B@48ms加锁  : A@42ms B@89ms C@155ms文件里最后留下: C

不加锁时三者的落地时刻几乎一样——它们真的在同时跑；加锁后间隔约 45ms（30ms 的 sleep + 开销），说明后一个在等前一个。判据不是「代码里有锁」，而是「时间被 拉开了」。

进程内锁的边界也要说清楚：它只挡同一个 Node 进程。两个 CLI 进程同时写一个文件， 它一点用都没有。那需要文件锁或原子重命名，属于另一章的事。

五、校验：模型给的参数永远别信

validateArgs 只做两件事：required 都在、类型对得上。不做嵌套、不做枚举、 不写完整的 JSON Schema。理由是：这一层的目标是「别把明显坏的参数喂给工具」， 不是「实现一个校验器」。工具自己仍然要检查语义（比如路径不能为空）。

真实输出里的第三行就是它：

text
err  c3 text 应该是 string，收到 number

注意报错文案里带上了「收到什么」——这是可修的报错和不可修的报错的分界。只写 「参数错误」，用户只能猜；写「收到 number」，他立刻知道模型把 "42" 写成了 42。

还有一个容易漏的点：校验失败不抛异常，而是返回一条 isError: true 的结果。 因为这是模型的问题，不是程序的问题。把它当异常抛，整个循环会崩；把它当消息 回给模型，它下一轮有机会自己改。

六、并发：Promise.all 为什么还能保序

ts
return Promise.all(calls.map((call) => runOne(call)));

Promise.all 返回的数组按输入顺序排列，不按完成顺序。这是规范行为，不是 实现巧合：下标是 promise 在数组里的位置。

所以模型看到的 tool 消息顺序和它发出的 toolCall 顺序一致——这对下一轮很关键。 多数 provider 要求 tool 结果紧跟在对应的 toolCall 后面，顺序错位就是 400。

代价是：一个慢工具会拖住整批的返回时刻，但不拖住别人开始。要「谁先好 谁先回」就得改成流式收集，那要动 AgentEvent（得有个「结果已就绪」的事件）， 留给 E07 的钩子一起做。

自检

  1. prev.then(fn) 和 prev.then(fn, fn) 差在哪？各举一个会出问题的场景。
  2. Promise.all 保序，是指「按完成顺序」还是「按输入顺序」？如果模型要求 tool 结果和 toolCall 一一对应，哪一处代码在保证这件事？
  3. 三个工具里有一个 sleep 10 秒，另外两个 30ms。runTools 的返回时刻是多少？ 如果想「先好的先回」，要改哪一层的契约？

参考答案：

第 1 题：prev.then(fn) 只在前一个成功时继续。前一个 write 失败（磁盘满、 权限拒绝）后，后面的写全部不执行，而且没有报错——因为异常已经被前一条链吞在 catch 里。prev.then(fn, fn) 两个分支都继续，失败只影响自己那一次。

第 2 题：按输入顺序。保证它的是 calls.map(...) 的顺序 + Promise.all 的下标语义；loop.ts 拿到的 results 和 calls 一一对应，写消息时不会错位。

第 3 题：约 10 秒——Promise.all 等最慢的那个。要「先好的先回」，得把 runTools 从「返回数组」改成「逐个 yield 结果」，同时给 AgentEvent 加一个 tool_result 事件；这是协议层改动，不是调度层。
