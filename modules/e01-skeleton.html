E01

骨架 —— 先用假模型，把循环跑通

2,201 字 · 含 73 行代码 · 约 12 分钟

M03 里那张「一次模型调用」的图，你可能已经看过三遍：发消息、收流、判断 stopReason、执行工具、把结果塞回去、再来一轮。看懂和写出来之间，隔着 一层很实在的东西——你会不会在第一次跑不通的时候，知道该怀疑哪一行。

这一章我们不看 Pi，先自己写一个 410 行的 mini-agent。它不 import 任何外部 依赖，模型是假的，工具只有两个，测试 11 个。目标不是做一个能用的 agent， 而是把循环的形状钉死；等你在 E04 打开真源码，会发现 Pi 多出来的全是 「在这根骨架上补的肉」。

三个问题，读完应该能答：

  1. 一个 agent 最小需要几个文件，各自负责什么？
  2. 模型只会说「我要调 read」，真正去调它的是谁？
  3. 循环有哪几种结束方式，凭什么说「停」？

先看全景。整条链路只有五个文件，箭头方向就是数据流方向：

text
  cli.ts        读一行输入，打印事件    |    v  loop.ts       外层轮次 / 内层工具，三处出口    |  \    |   \--> tools.ts    name + description + parameters + execute    v  provider/mock.ts      假模型：吐 chunk，不联网    |    v  types.ts      Message / Tool / Provider / AgentEvent 四个契约

一、先定形状，再写逻辑

新手写 agent 最常见的顺序是：先写 while 循环，再补消息类型，最后发现 「工具结果该放哪」想不清楚，回头改类型，循环也跟着改。

反过来做：先把四个契约写死。

types.ts 里最要紧的是这两个：

ts
export interface Tool {  name: string;  description: string;  parameters: {    type: "object";    properties: Record<string, ToolParameter>;    required: string[];  };  execute(args: Record<string, unknown>): Promise<string> | string;}

工具的四个字段不是随便凑的。name 是模型回传时的唯一凭据；description 是模型决定「要不要用它」的唯一依据；parameters 是 JSON Schema 的子集， 模型照着它填参数；execute 是唯一真正碰副作用的地方。

第二个是 provider：

ts
export interface Provider {  name: string;  stream(    messages: Message[],    tools: Tool[],    signal?: AbortSignal,  ): AsyncIterable<ProviderChunk>;}

注意它只收 Message[]，不收 AgentMessage[]。这条边界是 E02 的主角， 现在只要记住：给模型看的东西，比系统自己记的东西少。

二、假模型：三条规则，够用就好

真模型有三个麻烦：要 key、要网络、输出不确定。第一周就把这三样接进来， 你会把大量时间花在「为什么这次没返回工具调用」上，而不是循环本身。

provider/mock.ts 只有 39 行，规则三条：

  • 第一次调用、输入里有「读」、并且 read 有描述 → 发一条 toolCall
  • 已经有 tool 结果 → 回一句总结，停
  • 其余 → 原样回显，停

<!-- file: examples/mini-agent/src/provider/mock.ts -->

ts
      const wantsRead = /读|read/i.test(text);      if (!usedTool && read && read.description !== "" && wantsRead) {        yield { type: "text", text: "先看看文件。" };        yield {          type: "toolCall",          id: "call_1",          name: "read",          args: { path: "README.md" },        };        yield { type: "done", stopReason: "toolUse" };        return;      }

这段代码有两个刻意为之的地方，后面都会变成实验：

  1. read.description !== "" —— 描述是空的，假模型就不选它。真模型也一 样，只是它不会这么干脆。
  2. stopReason: "toolUse" —— 这一轮结束的原因是「我还想调工具」，不是 「我说完了」。整本书里所有「要不要再来一轮」的判断，都挂在这个字段上。

它吐的是 ProviderChunk，不是完整消息。流式的本质就是：先给增量，最后 给一个结论。结论只有一个字段，done.stopReason。

三、循环：一个 while，三处出口

先看最容易被写错的地方：谁执行工具。

不是 provider。provider 只负责说「我想调 read，参数是这个」。执行发生在 loop.ts，因为它才知道有哪些工具、失败要不要重试、结果怎么记。

核心就这几行：

<!-- file: examples/mini-agent/src/loop.ts -->

ts
    messages.push({ role: "assistant", content, stopReason: reason });    const calls = content.filter((b) => b.type === "toolCall");    if (calls.length === 0) {      emit({ type: "turn_end", turn: turns, stopReason: reason });      stop = reason;      break;    }

三件事按顺序发生：把 assistant 消息落进历史；从内容块里挑出工具调用； 没有工具调用就是这一轮的终点。

有工具调用时，逐个执行，把结果作为 tool 消息塞回历史，然后进入下一轮 while。这里有个容易忽略的细节：工具失败不算循环失败。

ts
        } catch (error) {          isError = true;          text = error instanceof Error ? error.message : String(error);        }

失败信息变成工具结果的一部分，模型下一轮能看见它，自己决定重试还是换路。 只有连续三次都失败，循环才以 error 收口：

ts
    if (errors >= MAX_TOOL_ERRORS) {      stop = "error";      break;    }

所以出口一共三处：

出口 触发条件 stopReason
正常收口 这一轮没有工具调用 provider 给的 stop / length
轮次用尽 到了 maxTurns，还想调工具 maxTurns
连续失败 工具连续 3 次抛错 error

Pi 的 packages/agent/src/agent-loop.ts 在结构上就是这两层：外层 while (true) 管轮次，内层 while (hasMoreToolCalls ...) 管工具； 遇到 stopReason === "error" 或 "aborted" 直接退出。区别只在它有 队列、有中断、有并发，骨架一样。

四、工具：一个形状，两个实现

tools.ts 里两个工具，一个读文件，一个回显。读文件这个值得逐行看：

<!-- file: examples/mini-agent/src/tools.ts -->

ts
  async execute(args) {    const file = String(args.path ?? "");    if (!file) throw new Error("path 不能为空");    const text = await readFile(file, "utf8");    const body = text.length > MAX_CHARS ? text.slice(0, MAX_CHARS) : text;    return `# ${file}（${text.length} 字符）\n${body}`;  },

三个决定，每个都有代价：

  • 参数再校验一次。 模型给的是 JSON，不是类型安全的对象；args.path 可能是 undefined，也可能是数字。String(... ?? "") 是最后一道防线。
  • 截断到 4000 字符。 工具返回值会立刻进上下文，一个 200KB 的日志能 把这一轮预算吃光。Pi 的 bash 工具也有类似的截断，M05 §七 专门讲过。
  • 失败就抛。 不要 return "读取失败"，因为那会被当成正常结果。抛错 后由循环包成 isError: true 的工具结果，模型能区分「文件内容」和 「读取失败」。

五、跑起来

在 examples/mini-agent 下：

bash
node src/cli.ts --mock "读 README"

真实输出（我本机 Node v24.12.0，两次逐字相同）：

text
[turn 1] 先看看文件。-> read [ok][turn 2] （mock）读完了，文件已经在上下文里。[stop]

四行输出对应四件事：第一轮模型说了半句、发了一个工具调用；工具执行成功； 第二轮模型看到工具结果，收尾；最终 stopReason 是 stop。

想确认消息确实存下来了，加 --print 看最后四条：

bash
node src/cli.ts --mock "读 README" --print

不看输出也行，test/loop.test.ts 里的第一个断言就是答案： ["user", "assistant", "tool", "assistant"]。

六、六组实验：每改一处，看一个数

# 改什么 预期看到 说明
1 --max-turns 1 [maxTurns]，消息 3 条 轮次用尽也算正常退出
2 mock 里 id 改成空字符串 工具结果 toolCallId 为空 真接口会 400（E03 验证）
3 删掉 read.description 不调用工具，直接回显 描述是模型选工具的唯一依据
4 输入「读 不存在」 [err]，但循环继续 工具失败不炸循环
5 同一条命令连跑两次 输出逐字节相同 假模型的价值：可复现
6 npm test 11 个测试全绿 事件顺序也在测

实验 2 值得先记一笔：toolCallId 唯一对应「哪次调用」，不是「哪个工具」。 模型并行发两个 read 时，只有 id 能区分结果归谁。真 provider 少这个字段 会直接拒绝请求。

实验 5 的判据是 diff，不是「看起来一样」：

bash
node src/cli.ts --mock "读 README" > a.txtnode src/cli.ts --mock "读 README" > b.txtfc /b a.txt b.txt

（PowerShell 下用 Compare-Object (Get-Content a.txt) (Get-Content b.txt)。）

七、小结

410 行，五个文件，循环的形状和三万行的 Pi 是同一个：消息进、流式出、 判断 stopReason、执行工具、回填、再来一轮。

这一章真正学到的不是「怎么写 while」，而是三件事：

  1. 先定契约，再写逻辑。 类型改一次，循环跟着改一次，成本是乘法的。
  2. 执行工具的是循环，不是模型。 模型只提案，循环才有权限。
  3. 失败是数据。 工具抛错变成一条带 isError 的结果，而不是异常冒泡。

十、三个常见误区

「provider 应该负责执行工具，因为它知道模型想要什么。」 它只知道「想要」，不知道「能不能」。权限、路径校验、超时、并发，全在宿主 这一侧。Pi 把 provider 放在 packages/ai，工具放在 coding-agent，就是 不让这两件事相互污染。

「工具报错就 return 一句错误文本，简单。」 那模型无法区分「命令输出里有 error 字样」和「命令根本没跑起来」。Pi 的 ToolResultMessage 有 isError 字段，就是为了让这两件事在类型上分开。

「maxTurns 只是防死循环的保险，平时用不到。」 它是产品语义：一次用户输入最多允许几轮工具。调小了任务做不完，调大了 一次误触能烧掉整月额度。E04 会把它当参数改一次，你会看到差别。

  2. read 抛错后，下一轮模型看到的消息长什么样？isError 在哪一层被设上？
  3. （L3） 如果让你把 while 换成递归，需要额外保存哪两个变量？为什么 Pi 没有这么写？

十二、下一步

骨架跑通了，但它现在只有一个角色：模型说什么，就原样发回去。真实会话里 还有系统提示、工具结果、压缩摘要、只给自己看的备注——它们不都是「给模型 看的消息」。
