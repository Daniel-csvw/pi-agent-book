M11

持久运行时 —— 把 Agent Loop 拆成状态机

9,300 字 · 含 364 行代码 · 约 45 分钟

M03 讲 runLoop 时，里面有两个 while：内层管模型与工具的锯齿，外层管续命。 当时有个前提一直没摆到台面上——进程还在跑。

packages/durable 的全部工作，是把这句话反过来：进程随时会消失，对话还得接着走。

33,728 行，harness/ 一个目录就占了 11,332 行。这不是会话存储包， 是一个完整的持久运行时。

零、读这章之前，你需要先知道一件事

三个类型层手法：Extract<A, B> = 从联合类型 A 里挑出能塞进 B 的那几支； brand（打标记的类型）= 给 string 盖个看不见的章，让它和别的 string 不能互换； never = 一个值都没有的类型，用来兜底"这里根本不该发生"。

没有它会怎样：把 Extract 当"过滤字符串"用，类型悄悄退化成 string， 编译不报错，直到运行时两个 id 串了才暴露。

本书哪里用到：§三 那 12 行最小片段；删掉它看错误信息怎么变。

先把最容易搞混的关系钉死。

1.1 两条互不相交的依赖线

看 coding-agent/package.json:44-45：依赖里有 pi-agent-core 和 pi-ai， 没有 pi-durable。

再看 durable/package.json 的 dependencies：

1.2 为什么可以不用 runLoop

runLoop 的价值是"管理锯齿"：模型给出 tool call，跑工具，把结果塞回去，再问一遍。 这件事在任何进程里都需要。

但"管理锯齿"有两种写法：

  • 栈上的循环：while 的进度是局部变量，进程死了就没了。
  • 状态机：每一步的进度是一次提交，进程死了从最后一步重来。

durable 选后者。所以它的循环不是一个函数，是一组phase 处理函数加一个调度器。 你在 generation.ts 里搜不到 while (hasMoreToolCalls)，搜到的是 phase: "tools"。

三、三个内核概念

entry、document、task。M10 讲了前两个，这里只补必要的差别，重点在第三个。

3.1 entry：不可变的历史

EntryRecord（types.ts:458-473）M10 拆过。这一章只需要记住一句话： entry 只追加，永远不改。所以它是"发生过什么"的唯一权威。

3.2 document：可以被改写的状态

AgentDoc 是最讲究的一个（harness/agent.ts:44-52）：

ts

四个字段各管一件事：

  • scope: "conversation"：每个会话一份 agent 配置，不是全局。
  • history: "rewindable"：每次改动都留版本，所以能读到"上个月那一刻"。
  • fork: "asOf"：分叉时拷分叉点那一刻的配置，不是拷现在这个。
  • checkpointWhen: () => true：任何改动都产生一个新版本，不合并。

checkpointWhen 是这套设计里最巧的一个钩子：它决定"这次改动要不要留一个可回读的快照"。 默认策略是按大小或时间算，而 agent 配置改一次就该记一次——所以直接返回 true。

3.3 task：第四种东西

entry 是"发生过什么"，document 是"现在是什么"，task 是**"接下来要做什么，做到哪了"**。

这是第一代完全没有的维度。M10 §7.2 说过：第一代的树里没有"这次调用成没成"这个概念， 所以只能在请求前补一个假的 No result provided。task 就是把那个缺口补上的类型。

TaskDefinition（types.ts:364-387）有六个字段：

ts
export type TaskDefinition<	I,	S extends { phase: string },	R,	H extends object,> = {	readonly name: string;          // 落到 TaskRecord.kind	readonly version: number;       // 落到 TaskRecord.version，用于迁移	initial(input: I): S;           // 第一个检查点	readonly phases: {		readonly [P in S["phase"]]: PhaseHandler<			I, Extract<S, { phase: P }>, S, R, H>;	};	abort(task, runtime, context): Promise<void>;	migrate?(input, checkpoint, fromVersion): {		input: I;		checkpoint: S;	};	readonly hooks?: H;};

三件事值得单独说：

一、phases 是穷举映射。 S["phase"] 是一个字面量联合，phases 必须每个都实现。 加一个 phase 忘了写处理函数，编译期就报错。

二、每个 handler 拿到的是"窄化后的任务"。 Extract<S, { phase: P }> 把联合类型 收窄到当前 phase，于是 task.state.checkpoint 在 prepare 里就是 prepare 的形状， 不需要在每个 handler 开头写 if。

三、migrate 在预留时跑，不在启动时跑。 一个一年前的 task 要等真正轮到自己 被调度时才迁移，所以旧版本的迁移代码不会在新进程启动时集中爆掉。

3.4 TaskRuntime：handler 能碰到的全部

每个 phase handler 签名的第二个参数是 runtime（types.ts:261-361）。它是任务唯一的 "手"——除了它，handler 没有别的途径读写世界。按用途分四组：

组 方法 干什么
写 commit(change, context, options?) 唯一写入口，返回新状态或 undefined
读 entry / entries / context / getTask 读已提交的 entry、上下文视图
编排 waitForTask / abortOwned / sleepUntil / outcomes 建关系和等结果
宿主 agent / settings / models / env / hooks / report 拿配置、跑钩子、报错

commit 的签名值得拄一遍（:290-297）：

ts
commit(	change: (tx: Tx, current: RunningTask<I, S, R>) =>		NextTaskState<S, R> | undefined		| Promise<NextTaskState<S, R> | undefined>,	context: Context,	options?: CommitOptions,): Promise<void>;

三个要点：

  • 回调里拿到的 current 是提交那一刻的任务记录，不是 handler 开头的快照。 中间可能已经过了一轮变更线，重读一遍才对。
  • 返回值是"下一个状态"。返回 undefined 表示"状态不变，只写了别的"。
  • 写操作全在 tx 上。注释里有一条警告（:286-287）：回调里只能用 tx 读， 用 snapshot() / watchDoc() 去读会排到自己持有的那条线上，永远不返回。 这是这套 API 最容易踩的一处死锁。

还有一个隐晦的约束：memo。两种签名——只读，或"没有就写、有就返回赢家"。 它是任务自己存的小值，随任务记录一起销毁，不占文档。

3.5 所有权：每个任务都得有个主人

TaskOptions.ownership 是必填字段（types.ts:406-407），注释写着 "a task always names its owner (spec §5.5)"。两种主人（:395）：

ts
export type TaskOwnership =	| { readonly kind: "conversation" }	| { readonly kind: "task"; readonly taskId: TaskId };
  • 会话拥有：顶层任务。一个 run 的 pi.generation 就是这样。
  • 任务拥有：子任务。一次工具调用 pi.tool 被它所在那轮 generation 拥有。

所有权不是装饰字段，它决定三件事：

  1. 谁等谁。waitForTask 只能等自己拥有的任务（types.ts:306-310）。
  2. 取消怎么传播。父任务取消，意图会传给下面的普通子任务（§5.6）。
  3. completing 什么时候结束。父任务宣布结局后，要等所有普通子任务终态。

还有两个标记：

  • background: true：会话拥有的任务，但排除在普通空闲等待、会话取消、级联之外。 常驻的后台任务用它。
  • abandonOnRestart: true：进程重启后就不该继续的任务。它会被打上 abortReason: "restart" 的标记走 abort 处理器，而不是变成 orphaned。

这两个标记解决同一类问题：这个任务还要不要跟着宿主一起活。 第一代根本没有这个问题，因为它没有任务。

四、六种状态，五种结局

4.1 TaskState（types.ts:658-702）

status 有调用栈吗 什么时候离开
pending 没有 被调度器预留 → running
running 有 handler 提交新检查点 → 仍是 running；或提交等待/睡眠/结局
waiting 没有 on 里所有任务都终态 → pending
sleeping 没有 时钟到 until → pending
completing 没有 它拥有的普通子任务全部终态 → terminal
terminal 没有 永不再变

注意 pending 和 running 的检查点类型完全一样。运行时状态不进检查点—— 这是整套设计的核心约定：检查点里只有"业务进度"，没有"我现在跑到哪一行"。

4.2 TaskOutcome（types.ts:621-655）

五种结局，区分得很细：

status 谁写的 含义
completed 任务自己 正常完成，带 result
failed 任务自己 预期内的失败，带 error
aborted abort 处理器 被取消，走完了自己定义的清理
orphaned 调度器 定义没了或迁移失败，这台机器上永远跑不了
faulted 调度器 契约破了：未捕获异常，或这一轮没产生持久进展

orphaned 和 faulted 的区别很实用：前者是"缺东西"，装上那个扩展就能继续； 后者是"代码有 bug"，重试一万次也一样。诊断时先看这个字段。

4.3 completing 为什么必须存在

这是六个状态里最反直觉的一个。

任务宣布了自己的结局，但它手上还有子任务在跑。如果立刻置 terminal， 子任务结束后就没有父任务可挂结果了。所以中间插一个 completing：

text
outcome 已定 ──> completing ──子任务全部终态──> terminal

types.ts:691-696 的注释写得很直白：

ts
/** Outcome decided; becomes terminal once no ordinary owned work * below is live. Runs no more code. */

"不再跑代码，但也不许收摊"——这一条正是第一代树结构做不出来的状态。 树里没有"父子任务的存活计数"这种东西。

4.4 为什么 finish 必须和 drain 分成两步

这是上面那条规则在代码里的直接后果，也是读 generation.ts 七个 phase 时最容易疑惑的地方： afterRun 钩子跑完就该结束了，何必再有一个 drain。

session/transaction.ts:1062-1065 有一条校验：

ts
/** * New owned work needs a live owner, judged on the owner's final * candidate: not `completing`, terminal, or abort-marked. A task * therefore cannot create owned work in the commit that finishes it * (spec §5.5). */async #validateOwners(): Promise<void> {

一次提交里，不许"建子任务"和"自己终结"同时发生。 #validateOwners 在组装阶段 （commit 真正落盘之前）遍历这次提交里所有新写的主任务 id，主人的候选状态只要是 completing / terminal / abort-marked，直接抛错。

所以 afterRun 钩子要建任务时，finish 只能先做一次不终结的提交 （generation.ts:899-915 的 holdRun）：

ts
// generation.ts:914-915（Commit A：不终结，只换 phase）const summary: RunSummary = { ...end, first: run.first ?? end.answer };return { status: "running", checkpoint: { phase: "finish", run: summary } };

这段代码把 §4.3 那句话变成了可执行的规则： completing 不只是"等子任务结束"的状态，它还是一条"不许再招人"的边界。 两个 phase，就是这条边界在时间上的投影。

五、调度器：没有循环的循环

scheduler.ts 3,159 行，是全包最重的一块。抓四个函数就够理解它了。

5.1 一次 kick，一轮 drain

ts
// scheduler.ts:1865-1888#kick(): void {	this.#scheduleWake();	this.#dirty = true;	if (this.#draining || !this.#enabled || this.#closing) return;	this.#draining = true;	// Never commit synchronously from a commit or registry listener.	queueMicrotask(() => void this.#drain());}async #drain(): Promise<void> {	try {		while (this.#dirty && this.#enabled && !this.#closing) {			this.#dirty = false;			const reservations = await this.#reserve();			for (const reservation of reservations) this.#start(reservation);		}	} catch (error) {		this.#failSession(error);	} finally {		this.#draining = false;		if (this.#dirty) this.#kick();	}}

这是 scheduler.ts 里唯一的调度循环——文件里另有五个 while， 都在向上走归属链或跑任务阶段，只有这一个管"这一轮有没有新活"。

三个细节：

  • queueMicrotask：注释写着"永远不要从提交回调或注册表监听器里同步提交"。 否则一次提交里套另一次提交，变更线会自己咬自己。
  • finally 里再 kick 一次：循环最后一轮检查之后到达的唤醒不能丢。
  • #failSession：预留阶段抛错，整个 Session 判死（M10 §10.4）。调度器不做局部恢复。

5.2 #reserve：一次提交预留所有活

#reserve（:1894-1988）做的事，用大白话说：

  1. 如果一个任务被"放弃重启"标记过，先给它打 abort 标记，这一轮就返回（下次再看）。
  2. 扫出这一轮所有可跑的候选。
  3. 对每个候选：检查重启次数上限、解析定义、必要时迁移、把状态写回 running。
  4. 全部写操作放进同一个 commitInternal。

第 3 步里那段"重启上限"值得抄一眼（:1932-1944）：

5.4 open()：把 running 改回 pending

进程重启后，文件里那些 running 的任务是什么状态？答案是：不知道。 可能跑完了没来得及提交，也可能刚到一半。

三件事一起发生：状态回 pending、检查点原样保留、restarts 加一。

"原样保留"是重点。上一轮跑到哪个 phase、那个 phase 的中间数据是什么，全在检查点里。 所以重跑不是从头来，是从最后一个已提交的阶段继续。

而 restarts 加一，就是 §5.2 那道闸的输入。这两个动作必须同时发生， 否则计数器就失去了"连续"的语义。

也就是说，一次"调用"（invocation）里可以连续跑好几个 phase，只要它们都在同一轮 并且每次都有持久进展。中途进程死了，检查点停在哪，下次就从哪接。

5.6 取消怎么往下传

取消不是"给每个任务发一个 signal"，而是一条从下往上确认的链。

#belowCancelled（:1702-1705）判一个任务头上有没有"取消意图"。 #planReservation 里（:2021-2024）：

ts

命中就不跑这个 phase，而是把这一轮标成"有待处理的级联"，然后安排一次 reconcile。

为什么不直接取消？因为 abort 是自下而上跑的（:2031-2032 的注释）： 子任务先清理完，父任务才能收尾。直接给父任务打 abort 标记，父任务会在子任务 还活着的时候就开始清理。

The waiting rule is also inverted: #waitingOn（:2034-2040）里，被 abort 标记的任务 要等的是它所有活着的普通子任务，不是 state.on 里那些。

用一张图说清三条边：

text
abortTask(parent)   |   +-> parent.abortRequested = true      （一次提交）   |   +-> parent 不再跑 phase，等 owned 全终态         |         +-> child 被级联标记 -> child 跑 abort 处理器 -> terminal               |               +-> 全部终态 -> parent 跑 abort 处理器 -> aborted

中间那一步是"标记"，不是"命令"。标记落盘之后，即使进程在中间死掉， 重启后 open() 会重新推导级联标记（:465-467）。 取消意图本身也是持久的。

5.7 提交点：一次 commit 到底保证什么

前面反复出现"一次提交"。现在把它打开——这是 session/transaction.ts(1,293) 的全部职责， 也是"中断后可恢复"能成立的地基。

Storage 接口（types.ts:1329）只有一个写方法：

ts
commit(	batches: readonly (readonly StorageWrite[])[],	receive: (index: number, seq: Seq) => void,	context: Context,): Promise<CommitResult>;

签名里装了四件事（:1330-1340 的注释）：

  1. 一个 batch 是一次原子提交，带自己的 seq，还要对照前一个 batch 留下的状态检查。
  2. 拒绝就停：某个 batch 被 durable 自己的校验拒了，前面的已经持久，它和后面的都没有。
  3. receive 是落盘回执，不是发布。它在全部落盘之后、下一个 commit 开始之前同步调用； Session 的对外发布在更后面。
  4. 结果是未知的就 reject（连接断了、语句或提交失败）；已发出的 receive 仍然算数。

第 3 条区分了两件常被混为一谈的事："写进存储"和"看到新值"。落盘成功但发布还没跑时 进程死掉，没问题——重启后从存储读就是新值。反过来，把发布当成落盘确认，就会丢数据。

Transaction implements Tx（transaction.ts:239）是接口上面那个对象。三条硬约束：

约束 出处 撞上了会怎样
表读必须在第一次表写之前 :277 的 #written 抛 ReadAfterWrite
读一个被未发布写者占着的 key :123 的 GatedStorage 等待，直到那个写者发布
回调抛错 :757 的 sealAfterFailure 所有 prepared 变更作废，一个字节不落盘

第一条解释了 prepareBoundary 的注释为什么强调 "Table reads must precede the commit's first table write"（inbox.ts:54-57）：边界要读队列和最新 head，这两次读必须在任何写之前完成。

第三条是"一个 phase 要么全成要么全不成"的来源。检查点和这一轮的副作用（追加 entry、 建子任务）在同一个回调里，所以不可能出现"记了进度但没做"或"做了但没记"。

还有一层更省的东西：HeldDocument / holdable()（:796-852）。不是每次 commit 都必须落盘。 一个只改 latest 文档、且改的是已有会话文档的提交，可以只在内存里推进，把变更攒着； 等某个 commit 真要落盘时，takeHeld() 把攒的变更排在自己前面，一起写。 语义上已提交，物理上延后——不是"拖批"，因为任何一个后来的落盘点都会把它们带上。

最后一步是 adopt（:904）：落盘成功后按指针交换更新缓存，不重读存储。 所以一次提交的代价是"一次批量写 + 一次指针交换"，而不是"写 + 全量重读"。

这一节和 §5.4 合起来，就是完整的恢复机制： 恢复的起点是最后一次落盘的 batch，而检查点保证那次 batch 里有一个完整可续的状态。

7.3 工具里还能再调工具

NestedCallDoc（tool.ts:117-125）解决的是另一类问题：工具 A 在执行中想调工具 B。

ts
export const NestedCallDoc = defineDocFamily<NestedCallState, null>({	kind: "pi.tool.nested-call",	version: 1,	scope: "task",	family: true,	initial: () => ({}),	// The document retires with its task.	checkpointWhen: () => false,});

一行一个槽位：family: true + initial: () => ({}) 意味着每次嵌套调用是这一族里的 一个新成员，读的时候按 key 取。

注释里那句"the result retires with the caller"是关键：嵌套调用的结果不写进 transcript， 它挂在调用者的文档上。所以对话历史里看不到它，调用者结束它也一起没了。 ToolTaskResult 因此是 { kind: "nested" }——只有一个标记，没有内容。

7.4 并行还是串行，是一个设置

settings.toolExecution（agent.ts:79）默认 "parallel"。

两种模式在代码里只差填 pending 的速度：

  • 并行：一次把这一轮所有调用建成任务，pending 立刻清空。
  • 串行：pending 留着剩下的调用，每轮只建一个（generation.ts:342-357）。

一份检查点里 tools 是"已经建过的任务"，pending 是"还没开始的调用"。 两个数组一起，就是这一轮的全部进度。

这也解释了 unoffered 那个标记的来由。version: 2 的迁移注释（generation.ts:166-168） 写得很具体：版本 1 会把"模型调了一个这轮没提供给它的工具"当成正常调用去解析名字； 版本 2 改成留一个 unoffered 标记，让它结算成 tool_unavailable。

为什么这需要版本号？ 因为检查点是跨版本读的。一个 v1 进程读到 v2 的检查点， 不知道怎么处理 unoffered，所以 #fit 直接判它 blocked，宁可不跑。

十一、工程暗坑

1. pending 和 running 的检查点类型一样，但不是一回事。 pending 表示没有调用栈，running 表示有人正持有它。靠检查点区分不了， 只能看状态字段。写恢复逻辑时不要拿检查点形状猜状态。

2. 规则 6 会咬人：phase 没产生持久进展就是 fault。 #rules（scheduler.ts:2297-2301）对比进出的检查点。你写一个只做副作用、 不提交的 handler，第一次跑就判 faulted。想"什么都不改就退出"， 得显式返回一个 waiting 或 sleeping 状态。

3. checkpointWhen 返回 false 的文档不会留下版本。 NestedCallDoc 就是 checkpointWhen: () => false，因为它跟着任务一起销毁。 给这种文档写"回到上一版"的逻辑会拿到 undefined。

4. replay 两边都是 safe 才重跑。 tool.ts:208 是 replay === "safe" && tool?.replay === "safe"。 只在自己那一侧写 safe、工具声明的是 unsafe，照样不重跑——这是故意的， 因为它防的是"工具的实现换了，重跑不再安全"。

5. restarts 只在"没改变过状态"时累加。 open() 里回退 running → pending 时加一。如果任务在被切断前改了检查点， 它大概率已经离开 running，下一次不会再加。连续才是这个计数器的语义。

6. abandonOnRestart 的任务不会变 orphaned。 它会带 abortReason: "restart" 等自己的定义，好让 abort 处理器清理干净 （scheduler.ts:1947-1952）。这类任务的 abort 处理器必须能处理"从没开始过"的情况。

7. orchestration 里有两种等待，别混。 waitForTask 等的是"任务终态"，是内存里的等待，调用结束就没； state.waiting 是持久等待，进程重启后仍然等。前者用来读结果，后者用来编排。

8. 延迟提交同样影响任务状态。 runtime.commit(..., PROGRESS_COMMIT) 是 persistWithinMs 那一档（默认 1 秒）。 任务的决策提交（返回新状态的那些）是立即的，只有纯文档改动可以延迟。 把这两类提交搞混，会在崩溃后看到"工具槽位显示 running 但任务已经 terminal"。

9. readOnly: true 打开的 Harness 什么都不恢复。 open() 里 if (this.#readOnly) continue; 跳过回退逻辑，running 任务保持原样 （另一个进程还在跑它）。所以只读端看到的 running 是真的在跑， 不是"上次没跑完"。

10. GenerationTask 的 version 是 2，ToolTask 是 3。 版本号不是包版本，是"检查点结构版本"。改 GenerationCheckpoint 的字段就必须加版本， 否则老检查点会被当成新结构读（prepare 里有专门处理旧版本缺字段的分支）。

11. commit 回调里只能用 tx 读。 types.ts:286-287 明确警告：回调里调 snapshot() / watchDoc() / getTask() 会排到自己持有的那条变更线上，然后永远不返回。这不是慢，是死锁。

12. pi.inbox 只在队列空的时候留版本。 inbox.ts:28 是 checkpointWhen: (value) => value.items.length === 0。 所以"把收件箱回滚到上一版"这种操作拿不到非空的旧状态——它压根没存。

13. 同一个 commit 里，表读必须在表写之前。 transaction.ts:277 的 #written 一旦置位，后续表读直接抛 ReadAfterWrite。 所以凡是"先读一下再决定写什么"的 phase，读都得摆在开头（prepareBoundary 就是这个形状）。 这条限制不在文档里，在错误里——撞上一次就记住了。

十三、收束

13.1 三个可迁移的方法

一、把"进度"从栈上搬到存储里，循环就自然消失了。 不是"给循环加个存档点"，是"循环本来就不该是一个函数"。 一个 while 的每次迭代如果都要持久化，那它就是一个状态机， 只是因为不需要崩溃恢复，被写成了循环的样子。

二、用"不产生进展即失败"兜住状态机的空转。 状态机最阴的 bug 是"什么都没发生，但也没报错"。 #rules 规则 6 用一个 jsonEqual 把这类 bug 变成可上报的 faulted。 这是状态机设计里性价比最高的一行代码。

三、不可逆的操作要先记意图，再执行。 tool.ts:195-198 那三行是整章最值得抄的一处：先提交"我要用什么参数跑什么工具"， 再跑。这样崩溃之后，系统知道"有一件事可能已经发生了"， 而不是"不知道发生过什么"——后者才是数据损坏的真正来源。
